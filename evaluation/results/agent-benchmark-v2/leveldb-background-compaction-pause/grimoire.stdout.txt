Investigation scope

Checked revision: `99b3c03b3284f5886f9ef9a4ef703d57373e61be` (LevelDB 1.23). The only worktree entries were the pre-existing discovery directories `.arcana/`, `.grimoire/`, and `.lexicon/`. No repository files were modified and no generators or tests were run.

Verified current behavior

1. Public surface and ownership

- `leveldb::DB` is the per-database public ownership object and is documented as safe for concurrent callers. Its only explicit compaction control is synchronous `CompactRange`; there is no pause/resume API (`include/leveldb/db.h:43-46`, `include/leveldb/db.h:137-147`).
- `DBImpl` is the concrete owner of the database’s compaction state. It implements `CompactRange`, owns the mutex and completion condition variable, and stores both the single scheduled/running flag and the pending manual-compaction pointer (`db/db_impl.h:29-50`, `db/db_impl.h:173-203`).
- The C API similarly exposes manual `leveldb_compact_range` but no automatic-compaction control (`include/leveldb/c.h:108-121`, `db/c.cc:263-270`).

This makes `DBImpl`’s per-instance scheduler—not `Env` and not `VersionSet`—the safest ownership seam.

2. One scheduler currently multiplexes three kinds of work

`MaybeScheduleCompaction` schedules the same `BGWork` callback whenever any of these is present:

- an immutable memtable (`imm_`);
- a manual request (`manual_compaction_`);
- an automatic level/seek compaction (`versions_->NeedsCompaction()`).

It records one boolean covering both queued and running work, then submits the callback through `Env::Schedule` (`db/db_impl.cc:662-677`).

`BackgroundCompaction` then chooses work in strict order:

1. flush `imm_` and return;
2. process `manual_compaction_`;
3. otherwise call `VersionSet::PickCompaction` for automatic work (`db/db_impl.cc:702-727`).

Consequently, “background” describes the execution mechanism, not ownership or intent: explicit manual compaction also executes through the background callback.

3. Manual compaction depends on that shared scheduler

- Public `CompactRange` first forces the current memtable to an SSTable and then invokes per-level manual compaction (`db/db_impl.cc:582-597`).
- `TEST_CompactRange`, which is the implementation path used by public `CompactRange`, installs a stack-owned `ManualCompaction` request, calls `MaybeScheduleCompaction`, and waits on `background_work_finished_signal_` until the request is done (`db/db_impl.cc:599-636`).
- `TEST_CompactMemTable` likewise forces a write-buffer rotation and waits while `imm_` remains non-null (`db/db_impl.cc:638-651`).
- A manual request can require multiple background callbacks: after each partial range, `BackgroundCompaction` advances the request’s begin key and clears `manual_compaction_`; the waiting caller reinstalls it and schedules the next segment (`db/db_impl.cc:768-780`, `db/db_impl.cc:622-630`).

Therefore, a blanket “paused” return at the top of `MaybeScheduleCompaction` would make explicit `CompactRange` wait forever.

4. Automatic work originates from several paths

Automatic level/seek compaction can be requested:

- after read statistics select a file (`db/db_impl.cc:1151-1155`);
- after explicit read sampling (`db/db_impl.cc:1174-1179`);
- after a memtable becomes immutable (`db/db_impl.cc:1376-1382`);
- on open/recovery (`db/db_impl.cc:1512-1515`);
- after every background callback, because one compaction can expose more work (`db/db_impl.cc:694-699`).

`VersionSet::NeedsCompaction` represents only table-level automatic work: it checks the computed size score and seek-selected file (`db/version_set.h:251-255`). `PickCompaction` chooses size work first, then seek work, and returns null if neither exists (`db/version_set.cc:1253-1286`).

5. Existing scheduling and concurrency constraints

- `background_compaction_scheduled_` deliberately means “scheduled or running,” preventing duplicate callbacks and allowing destruction to wait for outstanding work (`db/db_impl.h:195-198`, `db/db_impl.cc:152-159`).
- `BackgroundCall` currently always executes `BackgroundCompaction` unless shutting down or in background-error state. It then clears the scheduled flag, reschedules if needed, and signals all waiters (`db/db_impl.cc:683-700`).
- Actual table compaction releases `mutex_` while iterating and writing output, so a pause call can interleave with an already-running compaction; that operation cannot simply be made nonexistent after pause returns (`db/db_impl.cc:892-921`).
- During a table compaction, newly created immutable memtables are deliberately flushed with priority so writers can proceed (`db/db_impl.cc:921-933`).
- `Env` is the wrong seam: an `Env` can be shared and its scheduled functions are not even guaranteed to be serialized (`include/leveldb/env.h:192-198`). Blocking or filtering `Env::Schedule` would affect unrelated database instances and potentially unrelated background tasks.

Dangerous behavior to avoid

1. Do not pause immutable-memtable flushing.

When a memtable fills, `MakeRoomForWrite` installs it as `imm_` and schedules background work. A later write waits while that immutable table remains (`db/db_impl.cc:1351-1355`, `db/db_impl.cc:1371-1382`). Suppressing `imm_` work would turn a compaction pause into an immediate write deadlock after one additional full buffer. It would also deadlock the memtable-flush step at the start of explicit `CompactRange` (`db/db_impl.cc:582-595`, `db/db_impl.cc:638-646`).

2. Do not suppress manual requests.

A manual caller publishes a pointer to its stack request and waits for the shared worker (`db/db_impl.cc:604-630`). Refusing to schedule that request while paused leaves the caller blocked indefinitely and violates the central requirement.

3. Do not gate only new scheduling.

A callback may already be queued when pause acquires `DBImpl::mutex_`. Current `BackgroundCall` would still run automatic compaction unconditionally (`db/db_impl.cc:683-692`). The callback’s execution-time eligibility must also be checked.

4. Do not attempt to interrupt an in-flight table compaction.

Compaction creates pending output files, writes and verifies them with the mutex released, then installs a version edit and cleans up inputs and obsolete files (`db/db_impl.cc:800-889`, `db/db_impl.cc:892-921`). The existing mid-operation termination path is tied to database shutdown and dedicated cleanup (`db/db_impl.cc:783-797`, `db/db_impl.cc:921-933`). Reusing or imitating that path for pause would enlarge the change into cancellation/recovery logic and risk leaked pending outputs, incomplete metadata installation, or incorrect input lifetime.

The safe contract is: pause prevents queued and future automatic table compactions from starting; an automatic table compaction already in progress may finish.

5. Do not promise indefinite write availability.

Even with memtable flushing preserved, pausing table-to-table compaction allows L0 files to accumulate. Current policy starts automatic L0 compaction at four files, slows writes at eight, and stops writes at twelve (`db/dbformat.h:27-34`). `MakeRoomForWrite` implements those slowdown and stop behaviors (`db/db_impl.cc:1335-1346`, `db/db_impl.cc:1356-1359`). This is an expected operational consequence that the new API documentation must disclose.

Proposed design

The following is proposed behavior, not present in the checked-out revision.

API contract

Add per-DB methods named for intent rather than worker placement:

- `PauseAutomaticCompactions()`
- `ResumeAutomaticCompactions()`

Recommended documented semantics:

- Scope is one `DB` instance.
- Calls are safe concurrently with normal database operations.
- Pause is idempotent and non-blocking.
- It prevents queued and future automatic table-to-table compactions from starting.
- A table compaction already executing may complete.
- Immutable-memtable flushing and explicit `CompactRange` remain enabled.
- Resume is idempotent and promptly schedules any accumulated automatic work.
- Extended pauses may cause L0 write slowdown or blocking.

A boolean state is preferable to a nesting counter unless the API explicitly assigns pause ownership through a token. With plain paired methods, a counter makes an accidental duplicate pause permanently require duplicate resumes. If independent subsystems require composable ownership, that should instead be a separate RAII/token API, not an undocumented counter.

Minimal C++ implementation

1. `include/leveldb/db.h`
   - Add the two virtual methods with the contract above near `CompactRange`.
   - Making them pure virtual gives honest semantics but requires source changes in custom `DB` subclasses. A default no-op implementation would be source-compatible but dangerous because callers would believe compaction was paused when it was not.

2. `db/db_impl.h`
   - Override both methods publicly.
   - Add `bool automatic_compactions_paused_ GUARDED_BY(mutex_);` next to `background_compaction_scheduled_`.
   - Initialize it to false in the constructor.
   - The name should say “automatic”; naming it `background_compaction_paused_` invites future code to suppress manual requests and memtable flushing.

3. `db/db_impl.cc`
   - `PauseAutomaticCompactions`: lock `mutex_` and set the boolean true.
   - `ResumeAutomaticCompactions`: lock `mutex_`, clear the boolean, and call `MaybeScheduleCompaction`.
   - Refine `MaybeScheduleCompaction` so paused state suppresses only the `versions_->NeedsCompaction()` branch. In logical terms, work remains eligible whenever `imm_ != nullptr` or `manual_compaction_ != nullptr`; automatic `NeedsCompaction()` work is eligible only when not paused.
   - Add the same distinction in `BackgroundCall` before calling `BackgroundCompaction`. This closes the race where an automatic callback was queued before pause.
   - Do not alter `BackgroundCompaction`, `VersionSet`, compaction selection, or output cleanup.

4. `db/db_test.cc`
   - Update `ModelDB`, the only additional `DB` subclass in this checkout, to implement the new pure virtual methods (`db/db_test.cc:2046-2053`, `db/db_test.cc:2100-2108`).

5. C API, if the feature is intended for all supported callers
   - Add `leveldb_pause_automatic_compactions` and `leveldb_resume_automatic_compactions` beside `leveldb_compact_range` in `include/leveldb/c.h`.
   - Add one-line forwarding implementations beside the existing compact-range forwarding code in `db/c.cc`.
   - Add a C API smoke test. The behavioral concurrency tests should remain in C++ because the existing C test does not expose DB internals.

One subtle execution-time rule is required: if paused and a queued callback wakes with both `imm_` and `manual_compaction_` absent, it must skip `BackgroundCompaction`, clear `background_compaction_scheduled_`, run the normal rescheduling check—which now sees pause—and signal waiters. If a manual request or immutable memtable appeared after pause, the same queued callback may safely service it.

Minimal test plan

Use `db/db_test.cc`, whose fixture already exposes `DBImpl`, forces memtable flushes, counts table files by level, and builds overlapping tables (`db/db_test.cc:286-316`, `db/db_test.cc:407-464`).

Add a deterministic internal wait helper rather than using sleeps:

- `DBImpl::TEST_WaitForBackgroundWork()` should hold `mutex_` and wait while `background_compaction_scheduled_` is true.
- Because `BackgroundCall` clears the flag and invokes `MaybeScheduleCompaction` under the same mutex before signaling, this helper observes quiescence after the complete rescheduling chain, not a transient gap (`db/db_impl.cc:683-700`).
- Keep this helper explicitly test-only.

Tests:

1. `AutomaticCompactionsRemainPaused`
   - Pause immediately after opening an empty DB, ensuring there is no in-flight automatic compaction.
   - Create enough overlapping SSTables with repeated writes plus `TEST_CompactMemTable` to exceed `kL0_CompactionTrigger`.
   - Verify each forced flush returns and data remains readable; this proves immutable-memtable work was not paused.
   - Wait for background quiescence and assert L0 remains at or above the trigger instead of being automatically compacted.
   - This directly covers both scheduler-time suppression and the queued-callback execution check.

2. `ManualCompactionWorksWhileAutomaticCompactionsPaused`
   - While still paused with an automatic backlog, call public `db_->CompactRange(nullptr, nullptr)`.
   - Assert it returns, all inserted keys remain readable, and the L0/table distribution changes in the direction expected from manual compaction.
   - This catches the most dangerous regression: blanket suppression of the shared worker.

3. `ResumeSchedulesAccumulatedAutomaticWork`
   - Rebuild an automatic backlog while paused.
   - Call resume, then `TEST_WaitForBackgroundWork`.
   - Assert the backlog falls below the automatic trigger or otherwise verify the pre-resume L0 files were moved/merged, with all data intact.
   - Call resume a second time and verify it is harmless, establishing idempotence.

4. `PauseAndResumeAreIdempotent`
   - Pause twice, create a backlog, resume once, and verify work resumes. This locks in boolean—not reference-counted—semantics.
   - Pause/resume again after quiescence to cover the no-work path.

5. `QueuedAutomaticCallbackHonorsPause`
   - For deterministic race coverage, extend the test `Env` with a narrowly scoped scheduled-work barrier or queue counter: allow DBImpl to enqueue BG work, block before callback entry, call pause, then release it.
   - Assert the callback reaches quiescence without reducing the automatic backlog.
   - Avoid the existing one-second sleep style used by older automatic-compaction tests (`db/db_test.cc:765-773`); this race requires synchronization, not timing.

6. `InFlightCompactionMayFinish`
   - Block an automatic compaction after it has entered output work using a test-only `Env` barrier, call pause, release the barrier, and verify the operation completes cleanly.
   - Then create another automatic backlog and verify it remains pending until resume.
   - This validates the documented boundary between “already running may finish” and “no later automatic compaction starts.”

7. C API smoke test, if wrappers are added
   - Call pause, manual compact-range, and resume through C entry points and verify existing key reads still work. Existing compact-range coverage is at `db/c_test.c:214-220`.

Documentation rationale versus current behavior

- Current public documentation says manual compaction discards obsolete versions and rearranges storage and should be invoked only by users who understand the implementation (`include/leveldb/db.h:137-147`). The proposed pause documentation should use the same caution level.
- Current comments explain why L0 automatic compaction is driven by file count—L0 files are merged on every read and too many small files are expensive (`db/version_set.cc:1037-1052`). That is rationale for warning that a long pause can degrade reads and eventually stall writes; it is not evidence that pause currently exists.
- Current tests already regard read-triggered compaction as automatic behavior (`db/db_test.cc:739-773`) and dedicate a suite to proving reads eventually compact obsolete data (`db/autocompact_test.cc:57-103`). New tests should distinguish “automatic work suppressed” from “manual work unavailable.”
