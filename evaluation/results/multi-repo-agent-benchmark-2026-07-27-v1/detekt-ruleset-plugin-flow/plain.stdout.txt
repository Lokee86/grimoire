Repository files were not modified, and no generators were run. “Current behavior” below is verified at this revision; the test plan is explicitly proposed.

1. CLI plugin-input to loaded-provider flow

- The user-facing CLI surface is `--plugins`/`-p`. JCommander splits one argument using the platform path separator and first verifies that every path exists. The later core check is stricter: every path must have the case-sensitive extension `jar` (`detekt-cli/src/main/kotlin/dev/detekt/cli/CliArgs.kt:78-85`, `detekt-cli/src/main/kotlin/dev/detekt/cli/ArgumentConverters.kt:68-77`, `detekt-core/src/main/kotlin/dev/detekt/core/settings/ClassloaderAware.kt:22-26`).
- `CliArgs.createSpec` copies these paths into `extensions.fromPaths`; it also maps CLI configuration, activation, baseline, parallelism, reports, compiler options, and failure severity into one `ProcessingSpec` (`detekt-cli/src/main/kotlin/dev/detekt/cli/Spec.kt:38-80`).
- Normal CLI execution is `main` → `CliRunner.run` → `Runner.call`. `Runner` discovers the highest-priority `DetektProvider`, obtains a `Detekt`, and runs it. The core provider returns `AnalysisFacade` (`detekt-cli/src/main/kotlin/dev/detekt/cli/Main.kt:19-43`, `detekt-cli/src/main/kotlin/dev/detekt/cli/CliRunner.kt:16-32`, `detekt-cli/src/main/kotlin/dev/detekt/cli/runners/Runner.kt:32-36`, `detekt-tooling/src/main/kotlin/dev/detekt/tooling/api/DetektProvider.kt:23-32`, `detekt-core/src/main/kotlin/dev/detekt/core/tooling/DefaultDetektProvider.kt:7-10`).
- `ProcessingSettings` delegates plugin handling to `ExtensionFacade`. For path input, that facade creates a parent-first `URLClassLoader(pluginUrls, javaClass.classLoader)`. `createRuleProviders` then owns `ServiceLoader.load(RuleSetProvider::class.java, pluginLoader)` and filters disabled provider IDs (`detekt-core/src/main/kotlin/dev/detekt/core/ProcessingSettings.kt:29-39`, `detekt-core/src/main/kotlin/dev/detekt/core/settings/ClassloaderAware.kt:29-45`, `detekt-core/src/main/kotlin/dev/detekt/core/rules/RuleSets.kt:11-14`).
- Config generation follows a parallel special path: `ConfigExporter` builds an extension spec from `--plugins`, loads `DefaultConfigurationProvider`, and copies the merged default configuration (`detekt-cli/src/main/kotlin/dev/detekt/cli/runners/ConfigExporter.kt:8-18`).

2. Gradle configuration/task/worker flow for custom plugins

- The Gradle user surface is the resolvable, non-consumable, hidden, transitive `detektPlugins` configuration. Users normally add `dependencies { detektPlugins(...) }` (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/plugin/DetektBasePlugin.kt:59-65`, `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/plugin/DetektBasePlugin.kt:151`).
- `DetektPlugin` creates a separate transitive `detekt` configuration whose default dependency is `dev.detekt:detekt-cli:<toolVersion>`, then conventions every analysis, baseline, and generate-config task’s `pluginClasspath` to `detektPlugins` (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/plugin/DetektPlugin.kt:122-135`, `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/plugin/DetektPlugin.kt:137-172`).
- `Detekt` exposes `pluginClasspath` as a Gradle `@Classpath`. Its ordinary arguments contain input/config/baseline/reports/activation/severity/compiler flags, but deliberately do not contain `--plugins`; plugins are instead combined with `detektClasspath` as the runtime classpath (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:71-89`, `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:172-205`, `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:218-239`).
- Without the optional Worker API, `DefaultCliInvoker` receives that combined classpath directly. With `detekt.use.worker.api=true`, the task uses Gradle process isolation, submits the same combined classpath as work parameters, and `DetektWorkAction` invokes the same `DefaultCliInvoker` inside the worker (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/plugin/DetektPlugin.kt:191-192`, `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:221-239`, `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/invoke/DetektInvoker.kt:31-58`).
- `DefaultCliInvoker` creates/gets an isolated loader, reflectively loads `dev.detekt.cli.Main`, calls legacy `buildRunner`, and then calls `execute`. This is where Gradle converges with the CLI argument parser, `Runner`, `AnalysisFacade`, lifecycle, analyzer, baseline, and reporters (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/invoke/DetektInvoker.kt:61-78`, `detekt-cli/src/main/kotlin/dev/detekt/cli/Main.kt:46-66`).
- The important difference is plugin delivery: direct CLI uses `--plugins` and an inner core-created plugin loader; Gradle puts plugin JARs in the same isolated loader as detekt itself. Consequently Gradle’s parsed `args.plugins` is empty, and `ExtensionFacade` falls back to the running detekt classloader, which already contains the plugins (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:225-238`, `detekt-core/src/main/kotlin/dev/detekt/core/settings/ClassloaderAware.kt:32-44`).
- Analysis and baseline tasks have equivalent plugin-classpath wiring. Generate-config does too, allowing plugin `config/config.yml` resources to participate in generated configuration (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/DetektCreateBaselineTask.kt:187-207`, `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/DetektGenerateConfigTask.kt:49-72`).
- Gradle defaults and extension values are converted to CLI switches. Notably, `ignoreFailures=true` becomes `--fail-on-severity never`, and a configured analysis baseline is passed only if the file currently exists (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/internal/SharedTasks.kt:13-42`, `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/invoke/CliArgument.kt:87-97`, `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/invoke/CliArgument.kt:130-145`).

3. Classloader lifetime and service-discovery boundaries

- Direct CLI path plugins: `ExtensionFacade` creates a parent-first URL loader and closes it when `ProcessingSettings.use` exits. A caller-supplied loader is not closed by detekt (`detekt-core/src/main/kotlin/dev/detekt/core/settings/ClassloaderAware.kt:32-55`, `detekt-core/src/main/kotlin/dev/detekt/core/tooling/ProcessingSpecSettingsBridge.kt:28-40`).
- Verified lifetime caveat: default-config loading constructs a separate `ExtensionFacade(...).pluginLoader` but never closes that facade. `AnalysisFacade` always obtains a default configuration for `Lifecycle`, and an empty/default-building analysis can obtain another while constructing the effective configuration. Thus direct path-plugin runs can create additional URL loaders outside the settings-managed loader (`detekt-core/src/main/kotlin/dev/detekt/core/tooling/DefaultConfigProvider.kt:32-45`, `detekt-core/src/main/kotlin/dev/detekt/core/tooling/DefaultConfigProvider.kt:53-55`, `detekt-core/src/main/kotlin/dev/detekt/core/tooling/ProcessingSpecSettingsBridge.kt:61-75`, `detekt-core/src/main/kotlin/dev/detekt/core/tooling/AnalysisFacade.kt:22-29`).
- Gradle’s outer detekt loader is a parentless `URLClassLoader` containing both detekt and plugin files. It is cached globally by the hash code of the classpath set and has no close path in this implementation; ordinary Gradle invocation therefore reuses it for the lifetime of that Gradle plugin classloader, while Worker API use creates the analogous cache inside the isolated worker process (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/internal/ClassLoaderCache.kt:12-27`, `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/invoke/DetektInvoker.kt:39-67`).
- `RuleSetProvider`, `FileProcessListener`, `ConfigValidator`, `ReportingExtension`, `OutputReport`, and `ConsoleReport` are all independently discovered from the same `ProcessingSettings.pluginLoader`. Extensions other than rule-set providers are disabled by extension `id`, sorted by descending priority, and initialized with `ProcessingSettings` (`detekt-core/src/main/kotlin/dev/detekt/core/rules/RuleSets.kt:11-14`, `detekt-core/src/main/kotlin/dev/detekt/core/extensions/Loading.kt:10-25`, `detekt-core/src/main/kotlin/dev/detekt/core/FileProcessorLocator.kt:15-27`).
- `DetektProvider` discovery is a different boundary: it uses `DetektProvider`’s defining classloader and selects the maximum priority. Under Gradle that is the combined isolated loader, so a plugin can technically contribute a competing `DetektProvider`; under direct CLI `--plugins`, the plugin’s inner loader is not used for this earlier discovery (`detekt-tooling/src/main/kotlin/dev/detekt/tooling/api/DetektProvider.kt:23-32`, `detekt-cli/src/main/kotlin/dev/detekt/cli/runners/Runner.kt:32-35`).

4. Provider, rule factory, configuration, activation, and validation

- A provider must expose a valid `RuleSetId` and a no-argument service-instantiable implementation, then return a `RuleSet`. `RuleSetId` validates its identifier; `RuleSet(List<factory>)` probes every factory with `Config.empty` and indexes factories by the resulting `ruleName` (`detekt-api/src/main/kotlin/dev/detekt/api/RuleSetProvider.kt:9-20`, `detekt-api/src/main/kotlin/dev/detekt/api/RuleSet.kt:9-20`).
- With no restrictions, all discovered providers survive. `--disable-default-rulesets` removes only providers implementing the marker `DefaultRuleSetProvider`; it does not remove third-party providers. `--run-rule` finds the first matching provider ID and wraps one named factory (`detekt-core/src/main/kotlin/dev/detekt/core/rules/RuleSets.kt:15-33`, `detekt-api/src/main/kotlin/dev/detekt/api/internal/DefaultRuleSetProvider.kt:5-11`, `detekt-core/src/main/kotlin/dev/detekt/core/rules/SingleRuleProvider.kt:15-24`).
- `getRules` looks under configuration key `<provider.ruleSetId>`, calls `provider.instance()`, then enumerates configuration subkeys—not all factories in the returned `RuleSet`. Unknown configured rules are ignored; factories absent from configuration do not become descriptors (`detekt-core/src/main/kotlin/dev/detekt/core/RuleDescriptor.kt:24-56`).
- Activation is ruleset `active` defaulting to `true` AND rule `active` defaulting to `false`. Light analysis deactivates a `RequiresAnalysisApi` rule even when configured active. Severity is rule value, then parent ruleset value, then `Error`; invalid severity throws (`detekt-core/src/main/kotlin/dev/detekt/core/RuleDescriptor.kt:56-74`, `detekt-core/src/main/kotlin/dev/detekt/core/RuleDescriptor.kt:88-105`).
- `--all-rules` wraps configuration so undeclared `active` values read as true except for deprecated rules. Global auto-correction off wraps configuration to disable rule auto-correction (`detekt-core/src/main/kotlin/dev/detekt/core/tooling/ProcessingSpecSettingsBridge.kt:61-75`, `detekt-core/src/main/kotlin/dev/detekt/core/config/AllRulesConfig.kt:20-38`).
- Plugin JAR resources named `config/config.yml` are concatenated after detekt’s default config. They supply discoverable rule keys/defaults when default configuration is in use and provide the validation baseline (`detekt-core/src/main/kotlin/dev/detekt/core/tooling/DefaultConfigProvider.kt:32-45`, `detekt-core/src/main/kotlin/dev/detekt/core/tooling/DefaultConfigProvider.kt:53-55`).
- Validation occurs before parsing or provider execution. Plugin `ConfigValidator`s are loaded first; the built-in validator then excludes every non-`DefaultRuleSetProvider` namespace from ordinary default-property validation. Therefore third-party configuration is not exhaustively property-checked by the built-in validator unless the plugin supplies its own validator (`detekt-core/src/main/kotlin/dev/detekt/core/tooling/Lifecycle.kt:34-49`, `detekt-core/src/main/kotlin/dev/detekt/core/config/validation/ConfigValidation.kt:36-53`, `detekt-core/src/main/kotlin/dev/detekt/core/config/validation/DefaultPropertiesConfigValidator.kt:17-31`).
- A rule factory is invoked multiple times by design: once when a list-based `RuleSet` derives names, again with `Config.empty` for metadata while descriptors are built, and once per analyzed file with the effective rule config. Rules therefore are per-file instances, while the provider-created factory collection and processor instances are analysis-scoped (`detekt-api/src/main/kotlin/dev/detekt/api/RuleSet.kt:9-13`, `detekt-core/src/main/kotlin/dev/detekt/core/RuleDescriptor.kt:53-74`, `detekt-core/src/main/kotlin/dev/detekt/core/Analyzer.kt:64-80`).

5. Analyzer execution and concurrency/lifecycle behavior

- Lifecycle order is: validate config; obtain parsed files; validate classpath in full mode; load processors/providers/rule descriptors; retain active descriptors; call processors’ `onStart`; run analyzer; construct `Detektion`; fold processor `onFinish`; finally run reporting extensions (`detekt-core/src/main/kotlin/dev/detekt/core/tooling/Lifecycle.kt:34-59`).
- Synchronous analysis processes files in collection order. Parallel analysis creates one task per file on the shared `TaskPool`; all tasks share the same processor instances, but each task creates fresh rule instances for its file. Processor `onProcess` and `onProcessComplete` can therefore be concurrent, matching the API’s documented thread policy (`detekt-core/src/main/kotlin/dev/detekt/core/Analyzer.kt:30-62`, `detekt-core/src/main/kotlin/dev/detekt/core/Analyzer.kt:64-87`, `detekt-api/src/main/kotlin/dev/detekt/api/FileProcessListener.kt:12-36`).
- The default pool is a fixed pool sized to available processors and is shut down with settings; a caller-provided executor is not shut down (`detekt-core/src/main/kotlin/dev/detekt/core/TaskPool.kt:17-34`, `detekt-core/src/main/kotlin/dev/detekt/core/ProcessingSettings.kt:45-60`).
- A rule failure is wrapped with file, stack location, detekt/Java/OS context. In parallel mode that wrapper can subsequently be surfaced through `CompletableFuture.join` as a completion exception (`detekt-core/src/main/kotlin/dev/detekt/core/Analyzer.kt:40-61`, `detekt-core/src/main/kotlin/dev/detekt/core/Analyzer.kt:100-108`).
- Although CLI `--parallel` sets both `parallelParsing` and `parallelAnalysis`, the full-repository source search found no production core consumer of `parallelParsing`; current analyzer concurrency is controlled by `parallelAnalysis` (`detekt-cli/src/main/kotlin/dev/detekt/cli/Spec.kt:57-60`, `detekt-tooling/src/main/kotlin/dev/detekt/tooling/dsl/ExecutionSpecBuilder.kt:7-18`, `detekt-core/src/main/kotlin/dev/detekt/core/Analyzer.kt:30-37`).

6. Suppression and baseline ordering relative to findings

- Before execution, rules are filtered by ruleset/rule path includes and excludes. A file-level `@Suppress` matching rule ID, alias, ruleset ID, qualified ruleset/rule forms, or `all` prevents that rule from executing for the file (`detekt-core/src/main/kotlin/dev/detekt/core/Analyzer.kt:64-78`, `detekt-core/src/main/kotlin/dev/detekt/core/suppressors/Suppressions.kt:19-34`).
- After `Rule.visitFile`, finding-element annotation suppression runs, followed by configured `ignoreAnnotated`/`ignoreFunction` suppressors. Only surviving `Finding`s are transformed into `Issue`s, retaining any explicit `Finding.suppressReasons` (`detekt-core/src/main/kotlin/dev/detekt/core/Analyzer.kt:80-87`, `detekt-core/src/main/kotlin/dev/detekt/core/Analyzer.kt:91-98`, `detekt-core/src/main/kotlin/dev/detekt/core/Analyzer.kt:111-119`).
- Processor `onFinish` runs before reporting extensions. Reporting extensions see the raw post-processor result, then transform issues in descending priority order, then receive the final result (`detekt-core/src/main/kotlin/dev/detekt/core/tooling/Lifecycle.kt:51-59`, `detekt-core/src/main/kotlin/dev/detekt/core/extensions/Reporting.kt:8-14`, `detekt-core/src/main/kotlin/dev/detekt/core/extensions/Loading.kt:14-20`).
- Baseline handling is itself a service-loaded `ReportingExtension` with default priority `-1`. At its position in that extension chain, create mode first writes all incoming issue baseline IDs, then the same baseline is applied, so the run returns no newly baselined issues. Existing baseline IDs are removed from the issue list, not merely marked suppressed (`detekt-core/src/main/resources/META-INF/services/dev.detekt.api.ReportingExtension:1`, `detekt-api/src/main/kotlin/dev/detekt/api/Extension.kt:18-22`, `detekt-core/src/main/kotlin/dev/detekt/core/baseline/BaselineResultMapping.kt:24-45`, `detekt-core/src/main/kotlin/dev/detekt/core/baseline/BaselineResultMapping.kt:49-64`).
- Because custom reporting extensions can choose priorities above or below `-1`, baseline order relative to those transforms is extensible. Equal-priority extensions retain service-discovery encounter order; there is no explicit baseline tie-breaker in the sorter (`detekt-core/src/main/kotlin/dev/detekt/core/extensions/Loading.kt:14-20`, `detekt-api/src/main/kotlin/dev/detekt/api/Extension.kt:18-22`).

7. Finding aggregation, failure decisions, reporters, and output files

- Analyzer issues are flattened across files. `Detektion` contains those issues plus every configured rule descriptor’s `RuleInstance`, including inactive descriptors; only active descriptors are passed to the analyzer (`detekt-core/src/main/kotlin/dev/detekt/core/tooling/Lifecycle.kt:51-56`, `detekt-api/src/main/kotlin/dev/detekt/api/Detektion.kt:7-22`).
- Failure policy is evaluated after processor and reporting-extension transformations, including baseline filtering. It counts only final issues at or above the configured severity whose `suppressReasons` are empty. Baseline creation always suppresses failure for that run (`detekt-core/src/main/kotlin/dev/detekt/core/tooling/AnalysisFacade.kt:46-54`, `detekt-core/src/main/kotlin/dev/detekt/core/config/FailurePolicies.kt:8-31`).
- Output reports run before console reports. Each service-loaded `OutputReport` writes only when its `id` has a configured path; parent directories are created. An unknown configured report ID is silently unmatched. Standard console reports are independently loaded, priority-sorted, initialized, and written to the normal output channel (`detekt-core/src/main/kotlin/dev/detekt/core/reporting/OutputFacade.kt:14-52`, `detekt-core/src/main/kotlin/dev/detekt/core/reporting/OutputFacade.kt:60-75`).
- Standard issue console reports and Checkstyle/HTML/Markdown reports remove issues carrying `suppressReasons`; baseline-filtered issues are already absent. A custom output report receives the final `Detektion` and must choose whether to honor the `suppressed` flag itself (`detekt-core/src/main/kotlin/dev/detekt/core/reporting/console/AbstractIssuesReport.kt:20-28`, `detekt-report-checkstyle/src/main/kotlin/dev/detekt/report/xml/CheckstyleOutputReport.kt:19-42`, `detekt-report-html/src/main/kotlin/dev/detekt/report/html/HtmlOutputReport.kt:57-66`, `detekt-report-markdown/src/main/kotlin/dev/detekt/report/markdown/MarkdownOutputReport.kt:48-59`).
- Configuring two different report types to the same output path fails while constructing `OutputFacade`. Gradle additionally validates custom report IDs, destinations, and conflicts with built-in IDs before invocation (`detekt-core/src/main/kotlin/dev/detekt/core/reporting/OutputFacade.kt:14-24`, `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:259-274`).
- CLI `main` prints `InvalidConfig` and `IssuesFound` messages and exits 3 or 2; unexpected causes print a stack trace and exit 1. Successful runs exit 0 (`detekt-cli/src/main/kotlin/dev/detekt/cli/Main.kt:19-43`, `detekt-cli/src/main/kotlin/dev/detekt/cli/Main.kt:69-76`).
- Gradle translates reflected “Analysis failed with … issues” exceptions into a verification failure unless ignored; all other reflected failures become `GradleException` (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/invoke/DetektInvoker.kt:75-89`).
- Verified current defect: if `OutputFacade.run` throws an `Exception`, `AnalysisFacade` constructs an `UnexpectedError` result in the catch block but then discards it and unconditionally returns `DefaultAnalysisResult(detektion, fail)`. Report-generation exceptions are therefore swallowed at this layer; `Error` subclasses are not caught (`detekt-core/src/main/kotlin/dev/detekt/core/tooling/AnalysisFacade.kt:27-42`).

8. Important failure modes

- Missing CLI plugin paths fail during argument parsing; existing non-JARs fail while constructing settings. The extension check is case-sensitive, so `.JAR` is rejected (`detekt-cli/src/main/kotlin/dev/detekt/cli/ArgumentConverters.kt:72-77`, `detekt-core/src/main/kotlin/dev/detekt/core/settings/ClassloaderAware.kt:22-26`).
- A malformed service declaration, inaccessible/no-zero-argument provider, constructor failure, or binary linkage problem is not caught around `ServiceLoader` iteration. During analysis it reaches `AnalysisFacade`’s outer `runCatching` and becomes `UnexpectedError`; direct CLI prints the cause stack, while Gradle’s reflective runner rethrows the cause and normally converts the invocation wrapper to `GradleException` (`detekt-core/src/main/kotlin/dev/detekt/core/rules/RuleSets.kt:11-14`, `detekt-core/src/main/kotlin/dev/detekt/core/tooling/AnalysisFacade.kt:27-42`, `detekt-cli/src/main/kotlin/dev/detekt/cli/runners/Runner.kt:24-29`, `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/invoke/DetektInvoker.kt:64-89`).
- Gradle’s reflective invoker catches only `InvocationTargetException`; failure to load `dev.detekt.cli.Main`, method-signature mismatch, or other failure before reflective invocation propagates without `processResult` normalization (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/invoke/DetektInvoker.kt:64-78`).
- Gradle performs a Kotlin compiler binary-compatibility check in legacy `buildRunner`; direct `CliRunner` does not call this check. A detekt/plugin classpath compiled against a mismatched Kotlin compiler therefore has an explicit Gradle diagnostic but no equivalent direct-CLI preflight (`detekt-cli/src/main/kotlin/dev/detekt/cli/Main.kt:46-65`, `detekt-cli/src/main/kotlin/dev/detekt/cli/CliRunner.kt:16-32`).
- There is no provider-ID deduplication: all service instances are retained, and `getRules` flattens every provider. `--run-rule` selects the first matching ID. Duplicate provider IDs can therefore execute duplicate factories in unrestricted mode and are order-sensitive in single-rule mode (`detekt-core/src/main/kotlin/dev/detekt/core/rules/RuleSets.kt:11-31`, `detekt-core/src/main/kotlin/dev/detekt/core/RuleDescriptor.kt:24-41`).
- List-based `RuleSet` construction uses `associateBy`, so duplicate rule names in that list silently keep one factory rather than failing. There is also no check that the `RuleSet.id` returned by a provider matches `provider.ruleSetId`; configuration selection uses the provider ID while emitted `RuleInstance.ruleSetId` uses the returned rule-set ID (`detekt-api/src/main/kotlin/dev/detekt/api/RuleSet.kt:9-13`, `detekt-core/src/main/kotlin/dev/detekt/core/RuleDescriptor.kt:30-40`, `detekt-core/src/main/kotlin/dev/detekt/core/RuleDescriptor.kt:64-74`).
- Invalid plugin configuration can fail during validation, metadata creation, severity parsing, or per-file factory construction. Per-file failures are wrapped as analyzer failures; invalid validation notifications produce `InvalidConfig` before parsing (`detekt-core/src/main/kotlin/dev/detekt/core/config/validation/ConfigValidation.kt:36-53`, `detekt-core/src/main/kotlin/dev/detekt/core/RuleDescriptor.kt:94-105`, `detekt-core/src/main/kotlin/dev/detekt/core/Analyzer.kt:40-61`, `detekt-core/src/main/kotlin/dev/detekt/core/Analyzer.kt:100-108`).
- Gradle’s loader cache key is only the classpath set’s integer hash. Different classpath sets with a hash collision would share a loader; loaders are not closed by the cache (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/internal/ClassLoaderCache.kt:12-27`).
