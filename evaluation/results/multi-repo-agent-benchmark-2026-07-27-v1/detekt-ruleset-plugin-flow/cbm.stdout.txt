Current behavior verified from source at this revision. This was a read-only investigation; no files, generators, builds, or tests were run.

1. CLI plugin input → loaded provider

- The CLI accepts `--plugins`/`-p` as a platform-path-separator-delimited list. `PathConverter`, `PathSplitter`, and `PathValidator` parse and validate each supplied path before storing it in `CliArgs.plugins` (`detekt-cli/src/main/kotlin/dev/detekt/cli/CliArgs.kt:78-85`, symbol `CliArgs.plugins`).
- `CliArgs.createSpec` transfers those paths into `ProcessingSpec.extensionsSpec` via `fromPaths { args.plugins }`. The same mapping also carries rule activation, run policy, baseline, config, parallelism, and report destinations (`detekt-cli/src/main/kotlin/dev/detekt/cli/Spec.kt:15-82`, symbol `CliArgs.createSpec`).
- `buildRunner` checks that the runtime Kotlin compiler version exactly equals the version with which detekt was compiled, parses arguments, and creates a `Runner` for normal analysis (`detekt-cli/src/main/kotlin/dev/detekt/cli/Main.kt:46-68`, symbol `buildRunner`).
- `Runner.call` discovers the engine’s `DetektProvider`, asks it for a `Detekt`, and calls `run`; the default implementation produces `AnalysisFacade` (`detekt-cli/src/main/kotlin/dev/detekt/cli/runners/Runner.kt:32-36`, symbol `Runner.call`; `detekt-tooling/src/main/kotlin/dev/detekt/tooling/api/DetektProvider.kt:9-33`, symbol `DetektProvider.load`; `detekt-core/src/main/kotlin/dev/detekt/core/tooling/DefaultDetektProvider.kt:7-10`, symbol `DefaultDetektProvider.get`).
- `ProcessingSettings` delegates classloader behavior to an `ExtensionFacade` constructed from `extensionsSpec.plugins` (`detekt-core/src/main/kotlin/dev/detekt/core/ProcessingSettings.kt:29-62`, symbol `ProcessingSettings`).
- For CLI paths, `ExtensionFacade` first requires every path to exist and have the literal extension `jar`, then lazily creates one parent-first `URLClassLoader(plugin URLs, javaClass.classLoader)` shared by rule providers and all other extension kinds (`detekt-core/src/main/kotlin/dev/detekt/core/settings/ClassloaderAware.kt:16-45`, symbols `ExtensionFacade` and `pluginLoader`).
- `createRuleProviders` performs the actual `ServiceLoader.load(RuleSetProvider::class.java, pluginLoader)` iteration. It then removes explicitly disabled extension IDs and applies the configured run policy (`detekt-core/src/main/kotlin/dev/detekt/core/rules/RuleSets.kt:11-40`, symbol `ProcessingSettings.createRuleProviders`).

Thus, the CLI’s plugin JAR is not added to the JVM application classpath. It is placed behind a core-owned child `URLClassLoader`, and `RuleSetProvider` discovery is explicitly performed against that loader (`detekt-cli/src/main/kotlin/dev/detekt/cli/Spec.kt:62-65`, symbol `CliArgs.createSpec`; `detekt-core/src/main/kotlin/dev/detekt/core/settings/ClassloaderAware.kt:32-45`, symbol `ExtensionFacade.pluginLoader`; `detekt-core/src/main/kotlin/dev/detekt/core/rules/RuleSets.kt:11-13`, symbol `createRuleProviders`).

2. Gradle configuration/task/worker flow

- Applying the base Gradle plugin creates the hidden, resolvable, non-consumable, transitive `detektPlugins` configuration (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/plugin/DetektBasePlugin.kt:24-69`, symbol `DetektBasePlugin.apply`; `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/plugin/DetektBasePlugin.kt:151`, symbol `CONFIGURATION_DETEKT_PLUGINS`).
- Every `Detekt`, `DetektCreateBaselineTask`, and `DetektGenerateConfigTask` receives that configuration as its `pluginClasspath`; the analysis and baseline properties are annotated `@Classpath`, making plugin artifacts task inputs (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/plugin/DetektPlugin.kt:137-173`, symbol `DetektPlugin.setTaskDefaults`; `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:72-75`, symbol `Detekt.pluginClasspath`; `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/DetektCreateBaselineTask.kt:73-78`, symbol `DetektCreateBaselineTask.pluginClasspath`).
- Gradle translates source, config, baseline, rule options, severity policy, reports, compiler options, and related task settings into CLI arguments. Crucially, `pluginClasspath` is not included in this normal argument list (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:157-202`, symbol `Detekt.arguments`).
- With the Worker API enabled, `Detekt.check` uses `workerExecutor.processIsolation()`, submits `DetektWorkAction`, and places both `detektClasspath` and `pluginClasspath` in `DetektWorkParameters.classpath`. Without the Worker API it passes the same combined set directly to `DetektInvoker` (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:218-241`, symbol `Detekt.check`).
- Baseline creation uses the same combined classpath and invocation branches (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/DetektCreateBaselineTask.kt:187-208`, symbol `DetektCreateBaselineTask.baseline`).
- The worker action chooses dry-run or `DefaultCliInvoker`; normal execution delegates to `DefaultCliInvoker.invokeCli` (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/invoke/DetektInvoker.kt:39-59`, symbol `DetektWorkAction.execute`).
- `DefaultCliInvoker` obtains an isolated loader, reflectively loads `dev.detekt.cli.Main`, calls `buildRunner(args, System.out, System.err)`, and invokes the returned runner’s `execute()` (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/invoke/DetektInvoker.kt:61-79`, symbol `DefaultCliInvoker.invokeCli`).
- That loader is a null-parent `URLClassLoader` over the combined detekt/plugin classpath. It is cached globally by the hash of the classpath set and is not closed in this implementation (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/internal/ClassLoaderCache.kt:12-27`, symbols `DefaultClassLoaderCache.getOrCreate` and `GlobalClassLoaderCache`).
- Because Gradle’s normal argument list does not contain `--plugins`, the core receives no explicit plugin paths. Instead, `ExtensionFacade` falls back to `javaClass.classLoader`, which is the isolated combined loader that already contains the custom plugin (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:157-202`, symbol `Detekt.arguments`; `detekt-core/src/main/kotlin/dev/detekt/core/settings/ClassloaderAware.kt:32-45`, symbol `ExtensionFacade.pluginLoader`).
- `printCliCommand` is only a diagnostic reconstruction: it explicitly adds `--plugins` when displaying an equivalent standalone command (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:243-257`, symbol `Detekt.printCliCommand`).

The CLI and Gradle paths therefore converge at `Main.buildRunner` → `Runner` → `DetektProvider` → `AnalysisFacade` → `Lifecycle`. They differ before convergence: standalone CLI supplies plugin URLs in `ExtensionsSpec`, while Gradle runs the entire CLI/core/plugin set in one isolated reflective classloader (`detekt-cli/src/main/kotlin/dev/detekt/cli/Main.kt:46-68`, symbol `buildRunner`; `detekt-cli/src/main/kotlin/dev/detekt/cli/runners/Runner.kt:32-36`, symbol `Runner.call`; `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/invoke/DetektInvoker.kt:61-79`, symbol `DefaultCliInvoker.invokeCli`).

3. Classloader lifetime and service boundaries

There are three relevant discovery boundaries:

- Engine discovery: `DetektProvider.load` uses the classloader that loaded `DetektProvider`, chooses the maximum-priority provider, and errors if none exists (`detekt-tooling/src/main/kotlin/dev/detekt/tooling/api/DetektProvider.kt:23-32`, symbol `DetektProvider.load`).
- Rule-provider discovery: `createRuleProviders` uses `ProcessingSettings.pluginLoader` (`detekt-core/src/main/kotlin/dev/detekt/core/rules/RuleSets.kt:11-13`, symbol `createRuleProviders`).
- Other extension discovery—processors, config validators, reporting extensions, console reports, and output reports—uses the same `settings.pluginLoader`; instances are filtered by disabled ID, sorted by descending priority, and initialized before use (`detekt-core/src/main/kotlin/dev/detekt/core/extensions/Loading.kt:10-26`, symbol `loadExtensions`).

Lifetime:

- `ProcessingSpec.withSettings` wraps the settings in `use`, so settings are closed after analysis and output processing even on failure (`detekt-core/src/main/kotlin/dev/detekt/core/tooling/ProcessingSpecSettingsBridge.kt:23-41`, symbol `ProcessingSpec.withSettings`).
- `ProcessingSettings.close` closes the task pool and compiler environment and asks the extension facade to close its loader (`detekt-core/src/main/kotlin/dev/detekt/core/ProcessingSettings.kt:57-61`, symbol `ProcessingSettings.close`).
- `ExtensionFacade` closes only a loader it created from explicit plugin paths; externally supplied or fallback classloaders are not owned and are not closed (`detekt-core/src/main/kotlin/dev/detekt/core/settings/ClassloaderAware.kt:47-56`, symbols `ExtensionFacade.close` and `closeLoaderIfNeeded`).
- Consequently, the standalone CLI’s primary plugin loader is analysis-scoped, while Gradle’s combined loader is owned by `GlobalClassLoaderCache` and can live for the worker/daemon classloader-cache lifetime (`detekt-core/src/main/kotlin/dev/detekt/core/settings/ClassloaderAware.kt:51-56`, symbol `closeLoaderIfNeeded`; `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/internal/ClassLoaderCache.kt:12-27`, symbols `DefaultClassLoaderCache` and `GlobalClassLoaderCache`).
- There is an additional standalone-CLI lifetime concern: default configuration assembly constructs a separate `ExtensionFacade`, reads every `config/config.yml` resource, but does not close that facade. For explicit plugin paths this can create an extra unclosed URL loader during default-config loading (`detekt-core/src/main/kotlin/dev/detekt/core/tooling/DefaultConfigProvider.kt:32-46`, symbol `configInputStream`). This does not create another loader in the Gradle path because Gradle supplies no `ExtensionsSpec.paths`; the fallback is the already cached combined loader (`detekt-core/src/main/kotlin/dev/detekt/core/settings/ClassloaderAware.kt:32-45`, symbol `pluginLoader`).

4. Provider, factories, configuration, activation, and validation

Provider/factory model:

- A plugin provider exposes a `RuleSetId` and an `instance(): RuleSet`; its service registration is an explicit API requirement (`detekt-api/src/main/kotlin/dev/detekt/api/RuleSetProvider.kt:9-21`, symbol `RuleSetProvider`).
- A `RuleSet` contains rule-name-to-factory mappings. For each discovered provider, `getRules` obtains the ruleset-specific config and calls `provider.instance()` (`detekt-core/src/main/kotlin/dev/detekt/core/RuleDescriptor.kt:22-44`, symbols `getRules` and `RuleSetProvider.instance`).
- Rule discovery iterates configured keys, not every factory in the `RuleSet`. It ignores configured names absent from the provider map, probes each matching factory once with `Config.empty` for metadata/type checks, and retains the factory plus its actual rule config in a `RuleDescriptor` (`detekt-core/src/main/kotlin/dev/detekt/core/RuleDescriptor.kt:46-78`, symbol `RuleSet.getRules`).
- Therefore, a rule factory that has no corresponding config key is not scheduled merely because it exists in the plugin JAR. `--all-rules` changes `active` defaults for existing config keys but does not synthesize missing rule keys (`detekt-core/src/main/kotlin/dev/detekt/core/RuleDescriptor.kt:46-78`, symbol `RuleSet.getRules`; `detekt-core/src/main/kotlin/dev/detekt/core/config/AllRulesConfig.kt:10-31`, symbol `AllRulesConfig`).
- Plugins can contribute `config/config.yml`; default configuration concatenates detekt’s default YAML and all such resources visible to the plugin loader (`detekt-core/src/main/kotlin/dev/detekt/core/tooling/DefaultConfigProvider.kt:32-46`, symbol `configInputStream`).

Activation and severity:

- A rule is active only when its ruleset is active by default and the individual rule is active, with the individual default being false. In light analysis mode, a `RequiresAnalysisApi` rule is marked non-executable and logged rather than run (`detekt-core/src/main/kotlin/dev/detekt/core/RuleDescriptor.kt:55-77`, symbol `RuleSet.getRules`).
- `--all-rules` wraps configuration with `AllRulesConfig`, activating non-deprecated configured rules. Disabling auto-correction wraps config so `autoCorrect` always reads false. User/default config composition is then applied as requested or whenever no config was provided (`detekt-core/src/main/kotlin/dev/detekt/core/tooling/ProcessingSpecSettingsBridge.kt:61-78`, symbol `workaroundConfiguration`; `detekt-core/src/main/kotlin/dev/detekt/core/config/AllRulesConfig.kt:10-38`, symbol `AllRulesConfig`).
- Severity precedence is rule config, then ruleset config, then `Error`; an unrecognized severity throws during descriptor construction (`detekt-core/src/main/kotlin/dev/detekt/core/RuleDescriptor.kt:91-105`, symbols `Config.computeSeverity` and `parseToSeverity`).
- `DisableDefaultRuleSets` removes only providers implementing `DefaultRuleSetProvider`; third-party providers remain. Single-rule mode requires the named ruleset and rule and fails immediately if either is absent (`detekt-core/src/main/kotlin/dev/detekt/core/rules/RuleSets.kt:15-34`, symbol `createRuleProviders`; `detekt-core/src/main/kotlin/dev/detekt/core/rules/SingleRuleProvider.kt:8-27`, symbol `SingleRuleProvider.invoke`).

Validation:

- Validation runs before parsing and before final rule descriptor creation (`detekt-core/src/main/kotlin/dev/detekt/core/tooling/Lifecycle.kt:34-48`, symbol `Lifecycle.analyze`).
- It defaults from `config.validation`, loads plugin `ConfigValidator` extensions, adds the built-in validator, logs all notifications, and throws `InvalidConfig` if any error notification exists (`detekt-core/src/main/kotlin/dev/detekt/core/config/validation/ConfigValidation.kt:36-55`, symbol `checkConfiguration`).
- The built-in validator deliberately excludes every non-default provider’s entire `<ruleSetId>.*` namespace. Thus detekt’s default schema does not validate custom rule properties; a plugin must supply a `ConfigValidator` if it wants such validation (`detekt-core/src/main/kotlin/dev/detekt/core/config/validation/DefaultPropertiesConfigValidator.kt:17-32`, symbol `DefaultPropertiesConfigValidator.validate`).
- That exclusion calculation calls `createRuleProviders`, and the later loading phase calls it again, so service provider construction/discovery can occur during validation and again during rule loading (`detekt-core/src/main/kotlin/dev/detekt/core/config/validation/DefaultPropertiesConfigValidator.kt:18-22`, symbol `patterns`; `detekt-core/src/main/kotlin/dev/detekt/core/tooling/Lifecycle.kt:40-48`, symbol `Lifecycle.analyze`).

5. Analysis execution and concurrency/lifecycle

- `Lifecycle.analyze` performs, in order: config validation, parsing, optional full-mode classpath validation, processor/rule loading, processor `onStart`, analyzer execution, creation of `Detektion`, processor `onFinish` folds, and reporting-extension transformation (`detekt-core/src/main/kotlin/dev/detekt/core/tooling/Lifecycle.kt:34-60`, symbol `Lifecycle.analyze`).
- Only active `RuleDescriptor`s are supplied to `Analyzer`, but all discovered `RuleInstance` metadata—active and inactive—is retained in the resulting `Detektion` (`detekt-core/src/main/kotlin/dev/detekt/core/tooling/Lifecycle.kt:49-57`, symbol `Lifecycle.analyze`).
- `Analyzer.run` chooses synchronous or asynchronous file analysis from `executionSpec.parallelAnalysis` (`detekt-core/src/main/kotlin/dev/detekt/core/Analyzer.kt:30-38`, symbol `Analyzer.run`).
- Synchronous execution calls processor `onProcess`, analyzes one file, calls `onProcessComplete`, and aggregates issues by `flatMap` (`detekt-core/src/main/kotlin/dev/detekt/core/Analyzer.kt:40-49`, symbol `Analyzer.runSync`).
- Parallel execution creates one task per file in the shared `TaskPool`; processor file callbacks and rule execution happen inside those concurrent tasks, followed by `awaitAll(...).flatten()` (`detekt-core/src/main/kotlin/dev/detekt/core/Analyzer.kt:51-62`, symbol `Analyzer.runAsync`). Plugin processors used with parallel analysis must therefore tolerate concurrent per-file callbacks.
- For each file, path filters are applied first. Each surviving `RuleDescriptor` invokes its rule factory with the real rule config, so rule objects are per-file rather than shared across files. File-level suppression is then tested, and auto-correcting rules are partitioned to run before non-correcting rules regardless of registration order (`detekt-core/src/main/kotlin/dev/detekt/core/Analyzer.kt:64-80`, symbol `Analyzer.analyze`).
- `Rule.visitFile` clears its findings and runs `preVisit`, `visit`, and `postVisit` (`detekt-api/src/main/kotlin/dev/detekt/api/Rule.kt:41-48`, symbol `Rule.visitFile`).
- A per-file rule/factory failure is wrapped in an `IllegalStateException` containing the file, first stack location, original message, detekt/Java/OS versions, and original cause; both serial and parallel paths use that wrapper (`detekt-core/src/main/kotlin/dev/detekt/core/Analyzer.kt:40-62`, symbols `runSync` and `runAsync`; `detekt-core/src/main/kotlin/dev/detekt/core/Analyzer.kt:100-109`, symbol `throwIllegalStateException`).

6. Suppression and baseline ordering

Verified order:

1. Ruleset/rule path filters decide whether the rule is instantiated for the file.
2. The rule object is created.
3. File-level annotations suppress the entire rule before `visitFile`.
4. The rule emits raw `Finding`s.
5. Finding-element annotation suppression removes matching findings.
6. Rule-specific suppressors remove additional findings.
7. Remaining findings become `Issue`s.
8. Processor `onFinish` may transform the `Detektion`.
9. Reporting extensions receive raw results and transform issues in descending priority order.
10. `BaselineResultMapping`, as one reporting extension, creates/updates and/or filters the baseline.
11. Failure policy and output reporters consume the final transformed `Detektion`.

The first seven steps are explicit in `Analyzer.analyze` and `filterSuppressedFindings` (`detekt-core/src/main/kotlin/dev/detekt/core/Analyzer.kt:64-98`, symbols `Analyzer.analyze` and `filterSuppressedFindings`). Processor and reporting order is explicit in `Lifecycle.analyze` and `handleReportingExtensions` (`detekt-core/src/main/kotlin/dev/detekt/core/tooling/Lifecycle.kt:49-60`, symbol `Lifecycle.analyze`; `detekt-core/src/main/kotlin/dev/detekt/core/extensions/Reporting.kt:8-15`, symbol `handleReportingExtensions`).

Baseline specifics:

- Reporting extensions are sorted descending by `Extension.priority`; the API default is `-1`, and `BaselineResultMapping` does not override it. A third-party reporting transform with priority above or below `-1` can therefore run before or after baseline filtering (`detekt-core/src/main/kotlin/dev/detekt/core/extensions/Loading.kt:10-26`, symbol `loadExtensions`; `detekt-api/src/main/kotlin/dev/detekt/api/Extension.kt:22`, symbol `Extension.priority`; `detekt-core/src/main/kotlin/dev/detekt/core/baseline/BaselineResultMapping.kt:12-24`, symbol `BaselineResultMapping`).
- Baseline creation writes IDs from the already annotation/suppressor-filtered issue list, preserves the old manually-suppressed set, and then filters the same issues against the resulting baseline (`detekt-core/src/main/kotlin/dev/detekt/core/baseline/BaselineResultMapping.kt:33-62`, symbols `transformWithBaseline`, `filterByBaseline`, and `createOrUpdate`).
- Both `CurrentIssues` and `ManuallySuppressedIssues` suppress matching baseline IDs (`detekt-core/src/main/kotlin/dev/detekt/core/baseline/DefaultBaseline.kt:12-27`, symbol `DefaultBaseline.contains`).
- Baseline matches are removed from `Detektion.issues`; they are not retained merely with a baseline suppression flag (`detekt-core/src/main/kotlin/dev/detekt/core/baseline/BaselineResultMapping.kt:41-47`, symbol `filterByBaseline`).

7. Aggregation, severity/failure, reporters, and files

- Analyzer results are flattened into one issue list, combined with all rule metadata in `Detektion`, then passed through processor and reporting transformations (`detekt-core/src/main/kotlin/dev/detekt/core/Analyzer.kt:40-62`, symbols `runSync` and `runAsync`; `detekt-core/src/main/kotlin/dev/detekt/core/tooling/Lifecycle.kt:49-60`, symbol `Lifecycle.analyze`).
- Failure policy is either never-fail or fail-on-minimum-severity. It counts only final issues at or above the threshold whose `Issue.suppressed` property is false (`detekt-core/src/main/kotlin/dev/detekt/core/config/FailurePolicies.kt:8-29`, symbols `RulesSpec.FailurePolicy.check`, `checkForIssuesWithSeverity`, and `computeIssueCount`).
- Baseline creation forces a successful analysis result regardless of current issues, because those issues should be suppressed by the newly generated baseline on the next run (`detekt-core/src/main/kotlin/dev/detekt/core/tooling/AnalysisFacade.kt:46-55`, symbol `AnalysisFacade.checkFailurePolicy`).
- `OutputFacade` rejects configuration in which multiple report types target the same path. It then loads every `OutputReport` service, writes one only when its `id` has a configured destination, optionally prints successful file URIs, and finally renders enabled console reports (`detekt-core/src/main/kotlin/dev/detekt/core/reporting/OutputFacade.kt:14-55`, symbol `OutputFacade`).
- Console reports can be globally disabled or excluded by extension ID (`detekt-core/src/main/kotlin/dev/detekt/core/reporting/OutputFacade.kt:67-76`, symbol `loadConsoleReport`).
- Built-in issue console reports omit issues marked suppressed (`detekt-core/src/main/kotlin/dev/detekt/core/reporting/console/AbstractIssuesReport.kt:10-29`, symbol `AbstractIssuesReport.render`).
- Built-in Checkstyle, HTML, Markdown, and SARIF outputs also omit issues marked suppressed (`detekt-report-checkstyle/src/main/kotlin/dev/detekt/report/xml/CheckstyleOutputReport.kt:19-43`, symbol `CheckstyleOutputReport.render`; `detekt-report-html/src/main/kotlin/dev/detekt/report/html/HtmlOutputReport.kt:57-66`, symbol `HtmlOutputReport.render`; `detekt-report-markdown/src/main/kotlin/dev/detekt/report/markdown/MarkdownOutputReport.kt:48-65`, symbol `MarkdownOutputReport.render`; `detekt-report-sarif/src/main/kotlin/dev/detekt/report/sarif/Results.kt:14-15`, symbol `toResults`).
- Gradle configures default report destinations under the extension’s reports directory as task-specific `.html`, `.md`, `.sarif`, and `.xml` files, and passes custom reports as additional CLI report arguments (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/plugin/DetektPlugin.kt:137-164`, symbol `setTaskDefaults`; `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:259-275`, symbol `convertCustomReportsToArguments`).

Output/error propagation:

- Standalone `main` prints `InvalidConfig`/`IssuesFound` messages, prints argument help or unexpected stack traces, and exits 0/1/2/3 for success/unexpected/issues/config respectively (`detekt-cli/src/main/kotlin/dev/detekt/cli/Main.kt:19-44`, symbol `main`; `detekt-cli/src/main/kotlin/dev/detekt/cli/Main.kt:70-77`, symbol `AnalysisResult.exitCode`).
- Embeddable `Runner.execute` throws the original cause for `UnexpectedError` and throws typed detekt errors otherwise (`detekt-cli/src/main/kotlin/dev/detekt/cli/runners/Runner.kt:24-30`, symbol `Runner.execute`).
- Gradle catches the reflection wrapper. Analysis failures become verification failures unless `ignoreFailures` is true; all non-analysis failures become `GradleException` (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/invoke/DetektInvoker.kt:83-90`, symbol `processResult`).
- There is a verified current implementation anomaly in report-error propagation: `AnalysisFacade.runAnalysis` constructs `DefaultAnalysisResult(detektion, UnexpectedError(ex))` in the output catch block but discards it, then unconditionally returns `DefaultAnalysisResult(detektion, fail)`. Therefore an exception thrown only by `OutputFacade.run` is swallowed at this revision; it does not become the returned unexpected error (`detekt-core/src/main/kotlin/dev/detekt/core/tooling/AnalysisFacade.kt:27-44`, symbol `AnalysisFacade.runAnalysis`).

8. Important failure modes

- Missing or non-JAR standalone plugin paths fail during `ExtensionFacade` construction. Gradle does not pass explicit paths through this check; it treats resolved plugin artifacts as entries in the isolated classpath (`detekt-core/src/main/kotlin/dev/detekt/core/settings/ClassloaderAware.kt:16-27`, symbol `ExtensionFacade.init`; `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:218-241`, symbol `Detekt.check`).
- A JAR without a `RuleSetProvider` service entry is accepted as a JAR but contributes no rule provider because discovery is solely through `ServiceLoader` (`detekt-core/src/main/kotlin/dev/detekt/core/rules/RuleSets.kt:11-13`, symbol `createRuleProviders`).
- A malformed service descriptor, unconstructable provider, linkage failure, incompatible API signature, provider initialization failure, invalid severity, or rule-factory failure escapes the relevant loading/analyzer call and is converted by `AnalysisFacade` to `UnexpectedError`, except per-file rule failures first receive the detailed analyzer wrapper (`detekt-core/src/main/kotlin/dev/detekt/core/tooling/AnalysisFacade.kt:27-44`, symbol `runAnalysis`; `detekt-core/src/main/kotlin/dev/detekt/core/Analyzer.kt:100-109`, symbol `throwIllegalStateException`).
- Runtime Kotlin compiler mismatch is rejected before runner creation with an explicit unsupported-version message (`detekt-cli/src/main/kotlin/dev/detekt/cli/Main.kt:46-62`, symbol `buildRunner`).
- Gradle’s `detektPlugins` configuration is transitive, and its isolated loader has no parent. Consequently plugin-transitive copies of detekt/Kotlin classes participate directly in the combined URL classpath; the source has no dependency-version reconciliation check beyond the runtime Kotlin check in `buildRunner` (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/plugin/DetektBasePlugin.kt:58-65`, symbol `DetektBasePlugin.apply`; `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/internal/ClassLoaderCache.kt:16-24`, symbol `DefaultClassLoaderCache.getOrCreate`; `detekt-cli/src/main/kotlin/dev/detekt/cli/Main.kt:46-62`, symbol `buildRunner`).
- `createRuleProviders` does not group or reject equal `RuleSetId`s, and `getRules` flat-maps every provider. Distinct service providers with the same ID can therefore contribute duplicate rule descriptors/issues; only `ServiceLoader`’s handling of repeated declarations of the same provider class prevents an identical provider declaration from necessarily appearing twice (`detekt-core/src/main/kotlin/dev/detekt/core/rules/RuleSets.kt:11-40`, symbol `createRuleProviders`; `detekt-core/src/main/kotlin/dev/detekt/core/RuleDescriptor.kt:22-44`, symbol `getRules`).
- Unknown custom configuration is intentionally excluded from default validation. Bad custom values may fail only when the plugin’s probe or per-file factory reads them unless the plugin supplies a `ConfigValidator` (`detekt-core/src/main/kotlin/dev/detekt/core/config/validation/DefaultPropertiesConfigValidator.kt:17-32`, symbol `DefaultPropertiesConfigValidator.validate`; `detekt-core/src/main/kotlin/dev/detekt/core/RuleDescriptor.kt:46-78`, symbol `RuleSet.getRules`).
