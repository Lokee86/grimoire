Repository state remained read-only. I inspected the indexed lifecycle implementation and representative tests but did not execute tests, builds, generators, or proxy generation.

Current behavior is described in sections 1–8. Section 9 separates existing tests from the proposed test plan.

1. End-to-end normal lifecycle

Primary call/data flow:

`HikariDataSource.getConnection()`
→ `HikariPool.getConnection(connectionTimeout)`
→ `ConcurrentBag.borrow(remainingTimeout, MILLISECONDS)`
→ eviction/liveness check
→ borrow metrics and optional JDBC request boundary
→ `ProxyLeakTaskFactory.schedule(poolEntry)`
→ `PoolEntry.createProxyConnection(leakTask)`
→ application uses generated proxy
→ `ProxyConnection.close()`
→ statement cleanup, leak cancellation, rollback/reset/warning cleanup
→ `HikariPool.recycle(poolEntry)`
→ `ConcurrentBag.requite(poolEntry)`.

Concrete stages:

1. `HikariDataSource.getConnection()` first rejects an already-closed data source. If `fastPathPool` is available, it delegates immediately. Otherwise, lazy initialization is synchronized: configuration is validated, copied into a pool, sealed, and published before delegation. Pool-initialization failure is translated to `SQLTransientConnectionException`. `src/main/java/com/zaxxer/hikari/HikariDataSource.java:90-128` (`HikariDataSource.getConnection`).

2. `HikariPool.getConnection()` acquires the suspend/resume gate, starts checkout timing, and repeatedly borrows a `PoolEntry` from the bag. It rejects marked-evicted entries and stale entries that fail validation; a usable entry gets borrow metrics, an optional `Connection.beginRequest()`, a scheduled leak task, and a proxy. The suspend gate is released in `finally`. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:152-193` (`HikariPool.getConnection`).

3. Physical connections are supplied independently by pool-creation work. `PoolEntryCreator` calls `createPoolEntry()`, which calls `PoolBase.newConnection()`, wraps the physical JDBC connection in a `PoolEntry`, and installs lifetime/keepalive tasks. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:480-517` (`HikariPool.createPoolEntry`); `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:745-776` (`HikariPool.PoolEntryCreator.call`).

4. `PoolBase.newConnection()` obtains a physical connection using the configured `DataSource`, rejects a null result, initializes it, clears prior creation failure state, and returns it. If creation or setup fails, the partially created connection is physically closed and the failure is retained in `lastConnectionFailure`; connection-creation duration is recorded when metrics are enabled. `src/main/java/com/zaxxer/hikari/pool/PoolBase.java:360-408` (`PoolBase.newConnection`).

5. Initial physical state consists of validation/network-timeout setup, configured read-only and auto-commit values, driver capability checks, transaction isolation, catalog, schema, and `connectionInitSql`; the original network timeout is restored afterward. `src/main/java/com/zaxxer/hikari/pool/PoolBase.java:416-456` (`PoolBase.setupConnection`).

6. `PoolEntry.createProxyConnection()` optionally attaches a lease-tracking `WeakReference`, then passes the pool entry, physical connection, open-statement list, leak task, and configured state into `ProxyFactory.getProxyConnection()`. `src/main/java/com/zaxxer/hikari/pool/PoolEntry.java:101-110` (`PoolEntry.createProxyConnection`); `src/main/java/com/zaxxer/hikari/pool/ProxyFactory.java:46-49` (`ProxyFactory.getProxyConnection`).

7. Application `Connection.close()` closes the logical proxy, not normally the physical JDBC connection. After cleanup, it replaces the proxy delegate with a closed sentinel and calls `PoolEntry.recycle()`, which leads to `HikariPool.recycle()`. `src/main/java/com/zaxxer/hikari/pool/ProxyConnection.java:239-271` (`ProxyConnection.close`).

8. On a healthy return, `HikariPool.recycle()` records usage, updates the entry’s last-access time, optionally invokes `Connection.endRequest()`, and requites it to the bag. If already marked evicted, it closes rather than requites the entry. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:433-449` (`HikariPool.recycle`); `src/main/java/com/zaxxer/hikari/pool/PoolEntry.java:74-80` (`PoolEntry.recycle`).

9. `ConcurrentBag.requite()` changes the state back to `STATE_NOT_IN_USE`, preferentially offers it to waiting borrowers, and otherwise places it in the returning thread’s local cache. `src/main/java/com/zaxxer/hikari/util/ConcurrentBag.java:172-191` (`ConcurrentBag.requite`).

2. Acquisition-loop timing and timeout semantics

- Checkout timing begins after the suspend/resume gate has been acquired. Consequently, time blocked because the pool is administratively suspended is outside the configured connection-timeout measurement. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:156-160` (`HikariPool.getConnection`).

- The initial budget is the pool’s current `connectionTimeout`. After an evicted or dead candidate is closed, the loop computes `timeout = connectionTimeout - elapsedMillis(startTime)` and passes that remaining budget to the next bag borrow. A rejected candidate does not receive a fresh full timeout. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:158-171` (`HikariPool.getConnection`).

- `ConcurrentBag.borrow()` converts its timeout to nanoseconds and polls while more than 10 microseconds remain. The outer pool loop retries while more than the pool’s 10-millisecond soft floor remains. `src/main/java/com/zaxxer/hikari/util/ConcurrentBag.java:120-165` (`ConcurrentBag.borrow`); `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:166-184` (`HikariPool.getConnection`).

- The timeout is therefore a borrow/retry budget, not a separately enforced hard deadline around every operation. In particular, once a candidate is borrowed, its validation can consume additional time; if that candidate validates successfully, the method returns it without another deadline check. If it is dead, elapsed validation time is deducted before another iteration. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:162-184` (`HikariPool.getConnection`).

- Bag exhaustion breaks out and produces a `SQLTransientConnectionException`. The message contains elapsed time and total/active/idle/waiting counts; SQL state, vendor code, cause, and `nextException` preserve the most recent physical connection failure when it was a `SQLException`. Timeout metrics and a diagnostic pool-state log are emitted first. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:700-721` (`HikariPool.createTimeoutException`).

- If the handoff poll is interrupted, `HikariPool.getConnection()` restores the thread interrupt flag and throws `SQLTransientConnectionException("... Interrupted during connection acquisition")`. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:185-190` (`HikariPool.getConnection`).

- Suspension is different from bag interruption: `SuspendResumeLock.acquire()` waits uninterruptibly when suspended, unless system property `com.zaxxer.hikari.throwIfSuspended` is true, in which case it throws `SQLTransientException`. When suspension is disabled, the pool uses a no-op faux lock. `src/main/java/com/zaxxer/hikari/util/SuspendResumeLock.java:31-45` (`SuspendResumeLock.FAUX_LOCK`); `src/main/java/com/zaxxer/hikari/util/SuspendResumeLock.java:63-73` (`SuspendResumeLock.acquire`).

- `setConnectionTimeout(0)` maps to `Integer.MAX_VALUE`; configured connection and validation timeouts below the 250-ms soft floor are rejected or normalized by configuration validation. `src/main/java/com/zaxxer/hikari/HikariConfig.java:188-200` (`HikariConfig.setConnectionTimeout`); `src/main/java/com/zaxxer/hikari/HikariConfig.java:350-358` (`HikariConfig.setValidationTimeout`); `src/main/java/com/zaxxer/hikari/HikariConfig.java:1127-1136` (`HikariConfig.validateNumerics`).

3. `ConcurrentBag` coordination and pool growth

Borrowing order and ownership:

1. The caller first walks its thread-local list in reverse order, removing cached entries until one can atomically transition from `STATE_NOT_IN_USE` to `STATE_IN_USE`. `src/main/java/com/zaxxer/hikari/util/ConcurrentBag.java:126-138` (`ConcurrentBag.borrow`).

2. It then scans the shared list for the same state transition. If another waiter is already registered, a successful shared-list borrower asks the listener to compensate for that waiter. `src/main/java/com/zaxxer/hikari/util/ConcurrentBag.java:140-149` (`ConcurrentBag.borrow`).

3. If no entry is available, it increments the waiter count, calls `IBagStateListener.addBagItem(waiting)`, and polls the synchronous handoff queue. A handed-off entry is accepted only if the borrower wins its `STATE_NOT_IN_USE → STATE_IN_USE` transition. The waiter count is decremented in `finally`. `src/main/java/com/zaxxer/hikari/util/ConcurrentBag.java:151-168` (`ConcurrentBag.borrow`).

Producer behavior:

- `requite()` changes an in-use entry to available and repeatedly attempts a direct handoff while waiters exist. If no waiter accepts it, the entry is cached locally for that producer thread. `src/main/java/com/zaxxer/hikari/util/ConcurrentBag.java:172-191` (`ConcurrentBag.requite`).

- `add()` puts a newly created entry in the shared list, then repeatedly offers it through the handoff queue while waiters remain. Adding after the bag is closed is rejected. `src/main/java/com/zaxxer/hikari/util/ConcurrentBag.java:192-219` (`ConcurrentBag.add`).

Growth interaction:

- The bag listener is `HikariPool.addBagItem(waiting)`. It submits a `PoolEntryCreator` when waiting demand exceeds already queued creation work. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:457-463` (`HikariPool.addBagItem`).

- Connection creation is normally serialized by a one-core/one-max executor backed by a bounded queue; its worker is allowed to time out. The queue capacity is configured from `maximumPoolSize`. `src/main/java/com/zaxxer/hikari/util/UtilityElf.java:164-191` (`UtilityElf.createThreadPoolExecutor`); `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:109-114` (`HikariPool.HikariPool`).

- A creator continues only while the pool is normal, its worker is not interrupted, total connections remain below `maximumPoolSize`, and either idle count is below `minimumIdle` or waiter demand exceeds available idle entries. Creation failures retry with increasing backoff. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:745-787` (`HikariPool.PoolEntryCreator.call`, `shouldContinueCreating`).

- `fillPool()` separately computes a minimum-idle deficit while respecting maximum size and queued creation work. Thus waiter-driven growth and maintenance-driven minimum-idle fill share the same creator/executor constraints rather than independently exceeding capacity. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:525-538` (`HikariPool.fillPool`).

4. Validation, bypass, dead connections, and exception paths

Checkout validation:

- An entry marked evicted is always rejected. Otherwise, validation is bypassed if the entry was accessed within `aliveBypassWindowMs`, whose default is 500 ms and which can be changed by system property `com.zaxxer.hikari.aliveBypassWindowMs`. Older entries are passed to `isConnectionDead()`. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:61-64` (`HikariPool.aliveBypassWindowMs`); `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:162-171` (`HikariPool.getConnection`).

- JDBC4 validation uses `Connection.isValid(validationSeconds)` when no test query is configured. Otherwise it executes the configured query, applying a statement timeout when network timeout is unsupported. The physical connection’s normal network timeout is restored afterward, and isolated internal queries are rolled back when auto-commit is disabled. `src/main/java/com/zaxxer/hikari/pool/PoolBase.java:157-181` (`PoolBase.isConnectionDead`).

- Any validation exception is recorded as the last connection failure, logged, and treated as a dead connection. `src/main/java/com/zaxxer/hikari/pool/PoolBase.java:182-192` (`PoolBase.isConnectionDead`).

- A dead or evicted checkout candidate is removed and physically closed with an explanatory reason, then the remaining checkout budget is recomputed. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:162-171` (`HikariPool.getConnection`).

- Drivers lacking network-timeout support fall back to query-timeout granularity; HikariCP logs when sub-second or fractional-second validation timeout precision cannot be honored. `src/main/java/com/zaxxer/hikari/pool/PoolBase.java:547-572` (`PoolBase.getAndSetNetworkTimeout`).

Application SQL exceptions:

- `ProxyConnection.checkException()` examines up to ten exceptions in the chain. Unless a configured `SQLExceptionOverride` says `DO_NOT_EVICT`, fatal SQL-state prefixes, explicit fatal SQL states, designated vendor codes, or override `MUST_EVICT` mark the entry evicted. The proxy logs the broken connection, cancels the leak task, evicts the pool entry, and replaces its delegate with the closed sentinel. `src/main/java/com/zaxxer/hikari/pool/ProxyConnection.java:148-186` (`ProxyConnection.checkException`).

- The user-configurable `SQLExceptionOverride` is installed through sealed configuration and directly affects whether application exceptions retire the physical connection. `src/main/java/com/zaxxer/hikari/HikariConfig.java:940-974` (`HikariConfig.setExceptionOverrideClassName`, `setExceptionOverride`).

Creation and initialization failures:

- Physical creation failure closes a partially created connection and stores the throwable for later timeout diagnostics. `src/main/java/com/zaxxer/hikari/pool/PoolBase.java:383-408` (`PoolBase.newConnection`).

- Initial fail-fast handling can reject pool construction, particularly for connection setup errors, based on `initializationFailTimeout`. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:567-599` (`HikariPool.checkFailFast`).

5. Proxy close, recycle ownership, and state reset

- The proxy owns a `PoolEntry`, leak task, physical delegate, and tracked statement list. Created statements are wrapped and registered so they can be closed even if the application forgets them. `src/main/java/com/zaxxer/hikari/pool/ProxyConnection.java:51-64` (`ProxyConnection` fields); `src/main/java/com/zaxxer/hikari/pool/ProxyConnection.java:205-210` (`ProxyConnection.trackStatement`); `src/main/java/com/zaxxer/hikari/pool/ProxyConnection.java:282-364` (`ProxyConnection` statement factories).

- On logical close, `closeStatements()` runs first. A statement-close failure cancels leak tracking, evicts the pool entry, and closes the proxy delegate rather than exposing the physical connection to another borrower. `src/main/java/com/zaxxer/hikari/pool/ProxyConnection.java:212-236` (`ProxyConnection.closeStatements`).

- If the proxy remains open after statement cleanup, close cancels leak detection, rolls back dirty transactional work when auto-commit is off, resets dirty connection properties, and clears warnings. `src/main/java/com/zaxxer/hikari/pool/ProxyConnection.java:239-271` (`ProxyConnection.close`).

- Commit-dirty state is set by operations while auto-commit is disabled and cleared by full `commit()` or `rollback()`. It is distinct from the property dirty-bit mask. `src/main/java/com/zaxxer/hikari/pool/ProxyConnection.java:193-198` (`ProxyConnection.markCommitStateDirty`); `src/main/java/com/zaxxer/hikari/pool/ProxyConnection.java:375-389` (`ProxyConnection.commit`, `rollback`).

- Proxy setters mark only affected properties: read-only, auto-commit, transaction isolation, catalog, network timeout, and schema. `src/main/java/com/zaxxer/hikari/pool/ProxyConnection.java:409-415` (`setAutoCommit`); `src/main/java/com/zaxxer/hikari/pool/ProxyConnection.java:428-434` (`setReadOnly`); `src/main/java/com/zaxxer/hikari/pool/ProxyConnection.java:447-510` (`setTransactionIsolation`, `setCatalog`, `setNetworkTimeout`, `setSchema`).

- Return-time reset checks that dirty mask and restores only values that actually differ from pool defaults. `src/main/java/com/zaxxer/hikari/pool/PoolBase.java:213-251` (`PoolBase.resetConnectionState`).

- Cleanup occurs before the proxy delegate is replaced with `ClosedConnection.CLOSED_CONNECTION`; `PoolEntry.recycle()` is called from `finally`, so cleanup exceptions cannot silently strand the bag entry. A fatal exception makes the subsequent recycle path close the evicted entry; a nonfatal cleanup exception can still be propagated after recycling. `src/main/java/com/zaxxer/hikari/pool/ProxyConnection.java:243-271` (`ProxyConnection.close`); `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:433-449` (`HikariPool.recycle`).

- Optional JDBC request boundaries surround the checked-out lease: `beginRequest()` is attempted before proxy creation and `endRequest()` before healthy requite. Boundary failures are warnings and do not themselves fail checkout/recycle. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:172-181` (`HikariPool.getConnection`); `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:439-448` (`HikariPool.recycle`).

6. Leak detection

- At checkout, `ProxyLeakTaskFactory.schedule()` returns a no-op task when the threshold is zero; otherwise it creates a task containing the pool entry, borrowing thread name, and allocation stack, then schedules it on the housekeeping executor after the configured threshold. `src/main/java/com/zaxxer/hikari/pool/ProxyLeakTaskFactory.java:38-56` (`ProxyLeakTaskFactory.schedule`, `scheduleNewTask`); `src/main/java/com/zaxxer/hikari/pool/ProxyLeakTask.java:56-76` (`ProxyLeakTask.ProxyLeakTask`).

- When the delay expires, `ProxyLeakTask.run()` marks the lease leaked, trims internal stack frames, and logs an apparent connection leak with its allocation stack. It does not evict, abort, reclaim, or physically close the connection. `src/main/java/com/zaxxer/hikari/pool/ProxyLeakTask.java:78-95` (`ProxyLeakTask.run`).

- Logical proxy close cancels the scheduled leak task. If it had already fired, cancellation logs that the previously reported leaked connection was returned, i.e. “unleaked.” `src/main/java/com/zaxxer/hikari/pool/ProxyConnection.java:245-248` (`ProxyConnection.close`); `src/main/java/com/zaxxer/hikari/pool/ProxyLeakTask.java:97-104` (`ProxyLeakTask.cancel`).

- Configuration validation disables a production leak threshold below two seconds or above an enabled `maxLifetime`. `src/main/java/com/zaxxer/hikari/HikariConfig.java:1119-1125` (`HikariConfig.validateNumerics`).

7. Recycle, eviction, retirement, and physical close

Normal recycle:

- Healthy proxy close updates last-access state and returns the entry to the bag. An entry marked evicted while borrowed is physically closed instead. `src/main/java/com/zaxxer/hikari/pool/PoolEntry.java:74-80` (`PoolEntry.recycle`); `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:433-449` (`HikariPool.recycle`).

Soft eviction:

- `softEvictConnection()` marks the entry evicted. It closes immediately only if the caller owns the entry or can reserve an idle entry; otherwise an in-use entry remains available to its current borrower and closes when recycled. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:615-626` (`HikariPool.softEvictConnection`).

Maximum lifetime:

- `createPoolEntry()` schedules maximum lifetime with random negative variance so entries do not retire simultaneously. It also schedules keepalive with randomized variance. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:480-512` (`HikariPool.createPoolEntry`).

- `MaxLifetimeTask.run()` soft-evicts the entry and signals replacement demand. Thus idle entries can close immediately, while checked-out entries are marked and retired on return. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:861-874` (`HikariPool.MaxLifetimeTask.run`).

Idle timeout:

- The housekeeper snapshots idle entries, computes how many exceed `minimumIdle`, and reserves each candidate before checking/closing it. Reservation prevents checkout from winning the same entry. Idle retirement is disabled for fixed-size pools where minimum equals maximum. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:831-843` (`HikariPool.HouseKeeper.run`); `src/main/java/com/zaxxer/hikari/HikariConfig.java:1148-1150` (`HikariConfig.validateNumerics`).

Keepalive:

- `KeepaliveTask` reserves only an idle entry. A dead result is closed and replacement demand is signaled; a live result is unreserved and remains reusable. It never validates an entry currently owned by an application. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:883-902` (`HikariPool.KeepaliveTask.run`).

Physical close:

- `closeConnection()` first removes the entry from `ConcurrentBag`, detaches its physical connection through `PoolEntry.close()`, and submits asynchronous JDBC closure. After closure it requests replacement if the pool is still normal. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:465-478` (`HikariPool.closeConnection`).

- `PoolEntry.close()` cancels max-lifetime and keepalive futures, nulls the entry’s connection reference, and returns the detached physical connection to the caller. `src/main/java/com/zaxxer/hikari/pool/PoolEntry.java:170-184` (`PoolEntry.close`).

- `quietlyCloseConnection()` gives the physical connection a 15-second network timeout where supported and closes it via try-with-resources; close failures are logged and suppressed. `src/main/java/com/zaxxer/hikari/pool/PoolBase.java:137-155` (`PoolBase.quietlyCloseConnection`).

8. Housekeeping, shutdown, configuration, metrics/JMX, and observability

Housekeeper/fill interaction:

- The housekeeper refreshes runtime-adjustable connection timeout, validation timeout, leak threshold, idle timeout, minimum idle, maximum size, and catalog from the mutable configuration. It detects clock retrogression, soft-evicts on significant backward movement, warns about thread starvation or large forward clock leaps, performs idle cleanup, logs pool state, and finally calls `fillPool(true)`. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:799-850` (`HikariPool.HouseKeeper.run`).

- Because checkout demand calls `addBagItem()` immediately while housekeeping calls `fillPool()` periodically, acquisition does not wait for the next housekeeper run to request growth. Both routes converge on the bounded connection-adder executor and `PoolEntryCreator.shouldContinueCreating()`. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:457-463` (`HikariPool.addBagItem`); `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:525-538` (`HikariPool.fillPool`); `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:784-787` (`PoolEntryCreator.shouldContinueCreating`).

Shutdown:

- `HikariDataSource.close()` is idempotent through `isShutdown.getAndSet(true)`. It delegates to `HikariPool.shutdown()` and restores the calling thread’s interrupt status if shutdown itself is interrupted. `src/main/java/com/zaxxer/hikari/HikariDataSource.java:339-358` (`HikariDataSource.close`).

- Pool shutdown sets `POOL_SHUTDOWN`, cancels housekeeping, soft-evicts entries, stops the connection-adder, destroys housekeeping infrastructure, and closes the bag. It then repeatedly aborts active connections and evicts survivors for up to ten seconds, stops timeout/close executors, unregisters MBeans, and closes the metrics tracker. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:201-255` (`HikariPool.shutdown`).

- Active shutdown entries are detached, passed to JDBC `Connection.abort(assassinExecutor)`, and always removed from the bag. If `abort()` fails, HikariCP falls back to quiet physical close. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:545-559` (`HikariPool.abortActiveConnections`).

Configuration controls:

- Lifecycle-relevant controls include `connectionTimeout`, `validationTimeout`, `idleTimeout`, `maxLifetime`, `keepaliveTime`, `leakDetectionThreshold`, `minimumIdle`, `maximumPoolSize`, pool suspension, exception override, test query, transaction defaults, and initialization failure timeout. Numeric validation enforces interactions such as keepalive below max lifetime, meaningful idle timeout, minimum idle not exceeding maximum, and production leak-threshold limits. `src/main/java/com/zaxxer/hikari/HikariConfig.java:1101-1152` (`HikariConfig.validateNumerics`).

- Pool construction selects the real or faux suspension lock, performs fail-fast initialization, installs metrics and health checks, registers MBeans, creates add/close executors and leak-task factory, and starts housekeeping. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:88-132` (`HikariPool.HikariPool`).

Metrics/JMX/logging:

- Metrics can record physical creation duration, acquisition duration, lease usage duration, and timeout count. Pool-stat polling exposes waiting, idle, total, active, maximum, and minimum counts. `src/main/java/com/zaxxer/hikari/pool/PoolBase.java:399-407` (`PoolBase.newConnection`); `src/main/java/com/zaxxer/hikari/pool/PoolBase.java:741-786` (`PoolBase.MetricsTrackerDelegate`); `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:673-686` (`HikariPool.getPoolStats`).

- JMX-facing counts are directly derived from bag states and waiter count. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:352-377` (`getActiveConnections`, `getIdleConnections`, `getThreadsAwaitingConnection`).

- Debug pool-state logging reports total/max, idle/min, active, and waiting counts; it is used around housekeeping, creation, timeout, and shutdown paths. `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:419-426` (`HikariPool.logPoolState`).
