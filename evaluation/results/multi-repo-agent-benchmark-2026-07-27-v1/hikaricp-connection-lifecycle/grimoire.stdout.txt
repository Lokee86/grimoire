1. Normal end-to-end lifecycle

Concrete call/data flow:

`HikariDataSource.getConnection()`
→ `HikariPool.getConnection(connectionTimeout)`
→ `ConcurrentBag.borrow(timeout, MILLISECONDS)`
→ reject/close evicted or stale-and-dead entries
→ record borrow metrics
→ schedule `ProxyLeakTask`
→ `PoolEntry.createProxyConnection(...)`
→ application uses `ProxyConnection`
→ application calls `ProxyConnection.close()`
→ close statements, roll back dirty transaction if needed, reset changed state, clear warnings
→ cancel leak task
→ `PoolEntry.recycle()`
→ `HikariPool.recycle(poolEntry)`
→ `ConcurrentBag.requite(poolEntry)`

If the entry is evicted or broken, the return path instead becomes:

`ProxyConnection.close()` or `ProxyConnection.checkException()`
→ `PoolEntry.evict(...)`
→ `HikariPool.closeConnection(...)`
→ remove from `ConcurrentBag`
→ `PoolEntry.close()` detaches the physical connection and cancels lifetime/keepalive tasks
→ close executor calls `PoolBase.quietlyCloseConnection(...)`
→ underlying JDBC `Connection.close()`.

Public startup and entry point:

- The configuration-taking `HikariDataSource(HikariConfig)` validates and copies configuration, eagerly constructs `HikariPool`, stores it in both `pool` and `fastPathPool`, and seals configuration. The no-argument constructor leaves `fastPathPool` null for lazy startup (`src/main/java/com/zaxxer/hikari/HikariDataSource.java:45-88`, symbols `HikariDataSource()`, `HikariDataSource(HikariConfig)`).
- `HikariDataSource.getConnection()` rejects an already-closed data source, uses `fastPathPool` when eagerly initialized, otherwise performs synchronized double-checked initialization and translates a pool-initialization failure caused by `SQLException` back to that SQL exception (`src/main/java/com/zaxxer/hikari/HikariDataSource.java:90-135`, symbol `HikariDataSource.getConnection`).
- `HikariPool.getConnection()` supplies the configured `connectionTimeout` to `getConnection(long)` (`src/main/java/com/zaxxer/hikari/pool/HikariPool.java:134-163`, symbols `HikariPool.getConnection()`, `HikariPool.getConnection(long)`).

Physical connections are created asynchronously by `PoolEntryCreator`. It calls `createPoolEntry()`, which calls `newPoolEntry(...)`, then installs randomized max-lifetime and keepalive tasks before adding the entry to the bag (`src/main/java/com/zaxxer/hikari/pool/HikariPool.java:477-520`, symbols `HikariPool.createPoolEntry`, `PoolEntryCreator.call`). `PoolBase.newConnection(...)` invokes the configured `DataSource.getConnection(...)`, rejects a null result, runs `setupConnection`, clears prior failure state, and records connection-creation timing. A creation/setup failure quietly closes any partially created connection, records the last failure, and rethrows (`src/main/java/com/zaxxer/hikari/pool/PoolBase.java:365-408`, symbol `PoolBase.newConnection`). Setup applies network timeout, read-only, auto-commit, isolation, catalog, schema, and connection-init SQL, restoring the normal network timeout afterward (`src/main/java/com/zaxxer/hikari/pool/PoolBase.java:410-456`, symbol `PoolBase.setupConnection`).

2. Acquisition timing and timeout semantics

`HikariPool.getConnection(long hardTimeout)` first acquires `suspendResumeLock` and records a monotonic start time. It repeatedly asks `connectionBag.borrow(timeout, MILLISECONDS)`. If an entry is evicted or old enough to require validation and dead, it closes that entry and recomputes the remaining budget as `hardTimeout - elapsedMillis(startTime)` (`src/main/java/com/zaxxer/hikari/pool/HikariPool.java:134-168`, symbol `HikariPool.getConnection(long)`).

This is one overall acquisition budget, not a fresh timeout per rejected entry. The loop continues only while the recomputed remainder is positive. A successful entry records borrow statistics and becomes a proxy; exhaustion records borrow-timeout statistics and throws a timeout exception. Interruption restores the Java interrupt flag and throws `SQLException`; the suspension lock is always released in `finally` (`src/main/java/com/zaxxer/hikari/pool/HikariPool.java:165-210`, symbol `HikariPool.getConnection(long)`).

`createTimeoutException(startTime)` additionally records a connection-timeout metric and creates `SQLTransientConnectionException` containing elapsed time and total/active/idle/waiting counts. If physical creation previously failed, its SQL state, vendor code, cause, and next-exception relationship are retained (`src/main/java/com/zaxxer/hikari/pool/HikariPool.java:705-723`, symbol `HikariPool.createTimeoutException`).

Within `ConcurrentBag.borrow`, the handoff-queue timeout is converted to nanoseconds. If a polled entry loses its state race, elapsed poll time is subtracted before retrying; polling stops when approximately 10 microseconds or less remains. The waiter counter is decremented in `finally`, including timeout and interruption paths (`src/main/java/com/zaxxer/hikari/util/ConcurrentBag.java:174-218`, symbol `ConcurrentBag.borrow`).

Pool suspension precedes timeout accounting: `suspendResumeLock.acquire()` occurs before `startTime`. A suspended acquisition can therefore remain blocked until resume rather than consuming its configured acquisition budget. `suspendPool()` blocks new lock acquisition, while `resumePool()` returns the pool to normal, requests a fill, and resumes blocked callers (`src/main/java/com/zaxxer/hikari/pool/HikariPool.java:386-426`, symbols `HikariPool.suspendPool`, `HikariPool.resumePool`).

3. `ConcurrentBag` coordination and pool growth

`ConcurrentBag.borrow(...)` first scans and removes candidates from the current thread’s local cache, claiming one only through atomic `STATE_NOT_IN_USE → STATE_IN_USE`. If that fails, it increments `waiters`, scans the shared list with the same CAS, then asks the listener to grow the bag and polls the fair synchronous handoff queue (`src/main/java/com/zaxxer/hikari/util/ConcurrentBag.java:134-218`, symbol `ConcurrentBag.borrow`).

If a shared-list claimant may have taken an entry ahead of another waiter, it calls `listener.addBagItem(waiting - 1)`. If the shared scan finds nothing, it calls `listener.addBagItem(waiting)` before blocking (`src/main/java/com/zaxxer/hikari/util/ConcurrentBag.java:174-201`, symbol `ConcurrentBag.borrow`).

The pool implements that callback as `HikariPool.addBagItem(int)`: it submits a `PoolEntryCreator` when observed waiter demand exceeds the connection-adder executor’s queued work, avoiding an unconditional creation task for every callback (`src/main/java/com/zaxxer/hikari/pool/HikariPool.java:300-345`, symbol `HikariPool.addBagItem`).

`PoolEntryCreator.call()` retries physical creation with exponential backoff from 10 ms up to 5 seconds. It stops unless the pool is normal, its thread is not interrupted, total size is below maximum, and either idle count is below minimum or waiters outnumber idle connections (`src/main/java/com/zaxxer/hikari/pool/HikariPool.java:745-788`, symbols `PoolEntryCreator.call`, `PoolEntryCreator.shouldContinueCreating`).

On return, `ConcurrentBag.requite(...)` sets the entry to not-in-use and preferentially offers it directly to waiting borrowers. It parks or yields while contention remains; if nobody is waiting, it stores the entry in the returning thread’s local cache, capped at 16 entries (`src/main/java/com/zaxxer/hikari/util/ConcurrentBag.java:212-239`, symbol `ConcurrentBag.requite`). New entries are appended to `sharedList` and repeatedly offered to the handoff queue while waiters remain. Adding after bag closure throws `IllegalStateException` (`src/main/java/com/zaxxer/hikari/util/ConcurrentBag.java:240-265`, symbol `ConcurrentBag.add`).

4. Validation, bypass window, dead entries, and exceptions

Acquisition does not validate every checkout. `HikariPool` has a default 500 ms `aliveBypassWindowMs`; validation occurs only when time since `PoolEntry.lastAccessed` exceeds that window. Marked-evicted entries are rejected regardless. Rejected entries are removed and physically closed, and acquisition continues with the remaining original deadline (`src/main/java/com/zaxxer/hikari/pool/HikariPool.java:45-67`, field `aliveBypassWindowMs`; `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:157-178`, symbol `HikariPool.getConnection(long)`).

`PoolBase.isConnectionDead(...)` temporarily applies `validationTimeout`. It uses JDBC `Connection.isValid(...)` when no test query is configured; otherwise it executes the configured query, and rolls back the internal validation transaction when required. It restores the normal network timeout afterward. Any validation exception is logged as a failed validation and treated as a dead connection (`src/main/java/com/zaxxer/hikari/pool/PoolBase.java:143-182`, symbol `PoolBase.isConnectionDead`). The configurable validation timeout and optional test query are exposed by `HikariConfig` (`src/main/java/com/zaxxer/hikari/HikariConfig.java:342-385`, symbols `HikariConfig.setValidationTimeout`, `HikariConfig.setConnectionTestQuery`).

Runtime SQL failures pass through `ProxyConnection.checkException`. It walks at most ten linked SQL exceptions, allows an `SQLExceptionOverride` to force or suppress eviction, and otherwise treats SQLState class `08`, configured fatal states, and fatal vendor codes as broken-connection signals. On eviction it logs, cancels leak detection, evicts the entry, and replaces the delegate with `ClosedConnection` (`src/main/java/com/zaxxer/hikari/pool/ProxyConnection.java:131-174`, symbol `ProxyConnection.checkException`).

Physical creation failures are not converted into bogus bag entries. `createPoolEntry()` logs only while the pool is normal and returns null; `PoolEntryCreator` then backs off and retries while demand and pool state still justify creation (`src/main/java/com/zaxxer/hikari/pool/HikariPool.java:477-520`, symbols `HikariPool.createPoolEntry`, `PoolEntryCreator.call`). Timeout reporting carries the last creation failure as the timeout exception’s cause (`src/main/java/com/zaxxer/hikari/pool/HikariPool.java:705-723`, symbol `HikariPool.createTimeoutException`).

5. Proxy ownership, logical close, recycle, and state reset

A successful checkout schedules leak detection first and passes the resulting task to `PoolEntry.createProxyConnection(...)`; ownership is represented by the proxy while the `PoolEntry` remains in `STATE_IN_USE` (`src/main/java/com/zaxxer/hikari/pool/HikariPool.java:165-181`, symbol `HikariPool.getConnection(long)`; `src/main/java/com/zaxxer/hikari/pool/PoolEntry.java:85-127`, symbol `PoolEntry.createProxyConnection`).

The proxy tracks its owning `PoolEntry`, physical delegate, open statements, leak task, read-only and auto-commit state, transaction dirtiness, and dirty bits for mutable JDBC properties (`src/main/java/com/zaxxer/hikari/pool/ProxyConnection.java:46-129`, symbols `ProxyConnection`, `ProxyConnection.<init>`).

`ProxyConnection.close()` is a logical pool return. It cancels leak tracking, closes tracked statements, rolls back a dirty non-auto-commit transaction, resets only properties represented by dirty bits, and clears warnings. In `finally`, it replaces the delegate with `ClosedConnection.CLOSED_CONNECTION` and calls `poolEntry.recycle()`, preventing further use through that proxy (`src/main/java/com/zaxxer/hikari/pool/ProxyConnection.java:176-256`, symbols `ProxyConnection.closeStatements`, `ProxyConnection.close`).

`PoolBase.resetConnectionState(...)` restores only properties the proxy changed—read-only, auto-commit, transaction isolation, catalog, network timeout, and schema—and logs the reset bit mask (`src/main/java/com/zaxxer/hikari/pool/PoolBase.java:184-225`, symbol `PoolBase.resetConnectionState`). Existing tests verify that closing a proxy restores auto-commit and transaction isolation on the underlying connection (`src/test/java/com/zaxxer/hikari/pool/ConnectionStateTest.java:37-81`, symbols `ConnectionStateTest.testAutoCommit`, `ConnectionStateTest.testTransactionIsolation`).

`HikariPool.recycle(...)` records connection usage. A marked-evicted entry is closed rather than returned; otherwise optional JDBC request boundaries are ended and the entry is requited to the bag (`src/main/java/com/zaxxer/hikari/pool/HikariPool.java:428-450`, symbol `HikariPool.recycle`).

6. Leak detection

`ProxyLeakTaskFactory.schedule(...)` returns a no-op singleton when the threshold is zero. Otherwise it captures checkout context and schedules a task on the housekeeping executor after `leakDetectionThreshold` milliseconds. The housekeeper refreshes the factory’s threshold from runtime configuration (`src/main/java/com/zaxxer/hikari/pool/ProxyLeakTaskFactory.java:25-54`, symbols `ProxyLeakTaskFactory.schedule`, `ProxyLeakTaskFactory.updateLeakDetectionThreshold`; `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:790-808`, symbol `HouseKeeper.run`).

When fired, `ProxyLeakTask.run()` marks the connection apparently leaked, trims Hikari’s internal frames from the captured checkout stack, and emits a warning naming the connection and borrowing thread. `cancel()` cancels without interrupting; if the warning already fired, it logs that the connection was subsequently returned (“unleaked”) (`src/main/java/com/zaxxer/hikari/pool/ProxyLeakTask.java:49-95`, symbols `ProxyLeakTask.schedule`, `ProxyLeakTask.run`, `ProxyLeakTask.cancel`).

Cancellation occurs on normal proxy close and also before exception-driven broken-connection eviction, so a returned or definitively broken connection does not leave an active leak timer (`src/main/java/com/zaxxer/hikari/pool/ProxyConnection.java:131-174`, symbol `ProxyConnection.checkException`; `src/main/java/com/zaxxer/hikari/pool/ProxyConnection.java:212-256`, symbol `ProxyConnection.close`).

Configuration validation disables nonzero leak thresholds below 2 seconds or above an enabled max lifetime; defaults and numeric constraints are centralized in `HikariConfig.validateNumerics()` (`src/main/java/com/zaxxer/hikari/HikariConfig.java:1101-1170`, symbol `HikariConfig.validateNumerics`).

7. Recycle, eviction, retirement, and physical close

`HikariPool.closeConnection(...)` removes the entry from `ConcurrentBag`, calls `PoolEntry.close()` to detach its physical connection, and submits the actual JDBC close to a dedicated close executor. After closing, it calls `fillPool(false)` if the pool is still normal (`src/main/java/com/zaxxer/hikari/pool/HikariPool.java:451-474`, symbol `HikariPool.closeConnection`).

`PoolEntry.close()` cancels max-lifetime and keepalive futures, nulls those references and its connection reference, and returns the detached physical connection to the caller. This makes the pool entry cease owning that physical resource before asynchronous close begins (`src/main/java/com/zaxxer/hikari/pool/PoolEntry.java:175-196`, symbol `PoolEntry.close`). `PoolBase.quietlyCloseConnection(...)` applies a short network timeout and calls the physical connection’s `close()`, swallowing/logging close failures (`src/main/java/com/zaxxer/hikari/pool/PoolBase.java:227-272`, symbol `PoolBase.quietlyCloseConnection`).

Soft eviction first marks the entry. If the caller owns the checked-out proxy or the bag can reserve an idle entry, closure is immediate; otherwise the active entry remains marked and is closed on acquisition or recycle (`src/main/java/com/zaxxer/hikari/pool/HikariPool.java:601-635`, symbol `HikariPool.softEvictConnection`). Public `HikariDataSource.evictConnection(...)` only delegates for a live pool and a Hikari proxy (`src/main/java/com/zaxxer/hikari/HikariDataSource.java:321-336`, symbol `HikariDataSource.evictConnection`). Existing tests cover both close-after-marked-evicted and immediate public eviction (`src/test/java/com/zaxxer/hikari/pool/TestConnections.java:313-353`, symbols `TestConnections.testCloseMarkEvicted`, `TestConnections.testEviction`).

At creation, max lifetime is reduced by randomized variance to avoid a simultaneous mass expiry; keepalive is also jittered. Max-lifetime tasks soft-evict, and successful immediate eviction requests replacement for current waiters (`src/main/java/com/zaxxer/hikari/pool/HikariPool.java:477-506`, symbol `HikariPool.createPoolEntry`; `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:850-872`, symbol `MaxLifetimeTask.run`).

Keepalive reserves only idle entries. A dead entry is evicted and growth is requested; a live entry is unreserved and logged (`src/main/java/com/zaxxer/hikari/pool/HikariPool.java:874-891`, symbol `KeepaliveTask.run`).

8. Maintenance, shutdown, configuration, metrics/JMX, and observability

The pool constructor initializes fail-fast checking, metrics, health checks, MBeans, connection-adder and connection-closer executors, leak-task factory, and a fixed-delay housekeeper. Optional `com.zaxxer.hikari.blockUntilFilled` temporarily raises adder concurrency while initialization fills to `minimumIdle` (`src/main/java/com/zaxxer/hikari/pool/HikariPool.java:92-132`, symbol `HikariPool.<init>`).

The housekeeper refreshes runtime connection/validation/leak settings, detects retrograde clock changes and soft-evicts in that case, warns about starvation or forward clock leaps, retires only idle entries older than `idleTimeout` while preserving `minimumIdle`, and then invokes `fillPool(true)` (`src/main/java/com/zaxxer/hikari/pool/HikariPool.java:790-850`, symbol `HouseKeeper.run`). `fillPool(...)` queues enough creation tasks to restore minimum idle without exceeding maximum pool size (`src/main/java/com/zaxxer/hikari/pool/HikariPool.java:522-538`, symbol `HikariPool.fillPool`).

Thus acquisition-driven and maintenance-driven growth share the same connection-adder executor. Waiter callbacks request demand growth, while housekeeper/recycle/physical-close paths restore configured minimum idle. `PoolEntryCreator.shouldContinueCreating()` rechecks current pool state, capacity, idle count, and waiters before each creation, preventing stale queued work from blindly overfilling (`src/main/java/com/zaxxer/hikari/pool/HikariPool.java:300-345`, symbol `HikariPool.addBagItem`; `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:745-788`, symbol `PoolEntryCreator.shouldContinueCreating`).

Shutdown sets `POOL_SHUTDOWN`, cancels housekeeping, soft-evicts entries, stops creation, closes the bag, repeatedly aborts active connections and evicts remaining entries for up to ten seconds, shuts down network-timeout and close executors, unregisters MBeans, and closes metrics (`src/main/java/com/zaxxer/hikari/pool/HikariPool.java:195-255`, symbol `HikariPool.shutdown`). Active shutdown uses JDBC `Connection.abort(...)`, falling back to physical close, and removes entries in `finally` (`src/main/java/com/zaxxer/hikari/pool/HikariPool.java:540-559`, symbol `HikariPool.abortActiveConnections`). `HikariDataSource.close()` is idempotent and restores interruption if pool shutdown is interrupted (`src/main/java/com/zaxxer/hikari/HikariDataSource.java:337-358`, symbol `HikariDataSource.close`). Shutdown tests assert active, idle, and total counts all reach zero (`src/test/java/com/zaxxer/hikari/pool/ShutdownTest.java:130-173`, symbols `ShutdownTest.testShutdown2`, `ShutdownTest.testShutdown3`).

Relevant configuration defaults are 30-second connection timeout, 5-second validation timeout, 10-minute idle timeout, 30-minute max lifetime, 2-minute keepalive, and pool size 10 (`src/main/java/com/zaxxer/hikari/HikariConfig.java:49-70`, constants `CONNECTION_TIMEOUT`, `VALIDATION_TIMEOUT`, `IDLE_TIMEOUT`, `MAX_LIFETIME`, `DEFAULT_KEEPALIVE_TIME`, `DEFAULT_POOL_SIZE`). Numeric validation normalizes invalid timeout/lifetime/idle/keepalive relationships and notes that idle timeout has no effect in a fixed-size pool (`src/main/java/com/zaxxer/hikari/HikariConfig.java:1101-1170`, symbol `HikariConfig.validateNumerics`).

Metrics hooks on this lifecycle include physical creation time, borrow success, borrow timeout, connection timeout, usage duration, and tracker shutdown (`src/main/java/com/zaxxer/hikari/pool/PoolBase.java:365-408`, symbol `PoolBase.newConnection`; `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:165-188`, symbol `HikariPool.getConnection(long)`; `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:428-450`, symbol `HikariPool.recycle`; `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:705-723`, symbol `HikariPool.createTimeoutException`).

JMX exposes active, idle, total, and waiting counts plus soft eviction and suspend/resume operations; these counts come directly from bag state (`src/main/java/com/zaxxer/hikari/pool/HikariPool.java:347-426`, symbols `HikariPool.getActiveConnections`, `getIdleConnections`, `getTotalConnections`, `getThreadsAwaitingConnection`, `softEvictConnections`, `suspendPool`, `resumePool`). Debug logging exposes the same counts and configured capacity/minimum, while timeout exceptions include a point-in-time count snapshot (`src/main/java/com/zaxxer/hikari/pool/HikariPool.java:409-426`, symbol `HikariPool.logPoolState`; `src/main/java/com/zaxxer/hikari/pool/HikariPool.java:705-723`, symbol `HikariPool.createTimeoutException`).

9. Existing tests and focused proposed failure-mode plan

Verified existing coverage inspected:

- Physical creation retries honor at least the configured acquisition timeout (`src/test/java/com/zaxxer/hikari/pool/TestConnectionTimeoutRetry.java:45-90`, symbol `TestConnectionTimeoutRetry.testConnectionRetries`).
- Connection mutable state is reset on proxy close (`src/test/java/com/zaxxer/hikari/pool/ConnectionStateTest.java:37-81`, symbols `testAutoCommit`, `testTransactionIsolation`).
- Bag state transitions, borrow/requite, reserve, and invalid removal/unreserve diagnostics are exercised (`src/test/java/com/zaxxer/hikari/pool/TestConcurrentBag.java:49-95`, symbol `TestConcurrentBag.testConcurrentBag`).
- Concurrent checkout and eviction are stressed for 10,000 submissions (`src/test/java/com/zaxxer/hikari/pool/ConnectionRaceConditionTest.java:47-86`, symbol `ConnectionRaceConditionTest.testRaceCondition`).
- Eviction on proxy close and direct public eviction are asserted (`src/test/java/com/zaxxer/hikari/pool/TestConnections.java:313-353`, symbols `testCloseMarkEvicted`, `testEviction`).
- Shutdown is checked for zero active, idle, and total connections (`src/test/java/com/zaxxer/hikari/pool/ShutdownTest.java:130-173`, symbols `testShutdown2`, `testShutdown3`).
- Configuration validation tests exercise idle-timeout/max-lifetime normalization and invalid pool-size inputs (`src/test/java/com/zaxxer/hikari/pool/TestValidation.java:174-209`, symbols `validateIdleTimeout`, `validateInvalidMinIdle`, `validateInvalidMaxPoolSize`).

Proposed tests, not verified current behavior:

1. Deterministic deadline test: return a sequence of evicted/dead entries and assert all retries share one acquisition deadline rather than receiving a fresh timeout.
2. Interruption test: interrupt a thread blocked in `ConcurrentBag.borrow`, assert the thrown `SQLException` cause is `InterruptedException`, the interrupt flag remains set, and waiter count returns to zero.
3. Bypass-window test: use an injectable clock/validator to prove recently returned entries bypass validation while entries beyond the window invoke exactly one validation.
4. Waiter-growth race test: coordinate two waiters, shared-list theft, and a direct handoff; assert growth requests match outstanding demand and total size never exceeds maximum.
5. Logical-close failure matrix: independently fail statement close, rollback, state reset, warning clear, and leak cancellation; assert either safe recycle or eviction, never double ownership.
6. Leak test: verify no warning before threshold, one warning after threshold, cancellation before firing, and one “unleaked” notice after a reported proxy is returned.
7. Retirement race test: race max-lifetime, keepalive, application close, and explicit eviction; assert one physical close and cancellation of both scheduled entry tasks.
8. Shutdown-under-load test: combine blocked creation, active borrowers, idle entries, slow physical close, and interruption; assert bounded shutdown and zero bag entries.
9. Metrics test: assert exactly one success/timeout/usage/creation event per corresponding lifecycle outcome, including dead-entry retries.
10. Clock-maintenance test: simulate retrograde and large forward jumps, verifying soft eviction only for retrograde motion and no reduction below `minimumIdle` during idle cleanup.
