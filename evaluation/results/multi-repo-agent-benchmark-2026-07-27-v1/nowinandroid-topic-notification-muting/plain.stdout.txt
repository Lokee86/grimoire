4. Notification boundary and edge-case behavior

Proposed boundary

Keep filtering in `OfflineFirstNewsRepository.syncWith`, after the incoming resources and their fresh topic lists have been obtained but immediately before `Notifier.postNewsNotifications`. This matches current ownership: the repository knows change-list novelty, database existence, user data, and associations; `SystemTrayNotifier` only knows presentation (`core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/repository/OfflineFirstNewsRepository.kt:66-143`, `syncWith`; `core/notifications/src/main/kotlin/com/google/samples/apps/nowinandroid/core/notifications/SystemTrayNotifier.kt:52-104`, `postNewsNotifications`).

Concrete algorithm

1. Before upsert, obtain `existingChangedIds` by news ID only, not by followed topics. Current pre-detection filters by followed topics, which can misclassify an existing item when its topic associations change (`core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/repository/OfflineFirstNewsRepository.kt:79-94`, `existingNewsResourceIdsThatHaveChanged`).
2. While fetching each network batch, retain `freshTopicIdsByNewsId` from `NetworkNewsResource.topics`; that field defaults to an empty list (`core/network/src/main/kotlin/com/google/samples/apps/nowinandroid/core/network/model/NetworkNewsResource.kt:29-38`, `NetworkNewsResource.topics`).
3. Replace, rather than only append, cross-references for each changed news ID: add a DAO delete-by-news-IDs operation and invoke it before inserting the payload’s new references. The current `insertOrIgnoreTopicCrossRefEntities` can preserve removed associations indefinitely (`core/database/src/main/kotlin/com/google/samples/apps/nowinandroid/core/database/dao/NewsResourceDao.kt:99-108`, `insertOrIgnoreTopicCrossRefEntities`; `core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/repository/OfflineFirstNewsRepository.kt:119-124`, current insertion).
4. Suppress all notification posting when `isFirstSync` is true. Continue marking those IDs viewed (`core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/repository/OfflineFirstNewsRepository.kt:96-100`, first-sync behavior).
5. Immediately before filtering, take the final `userData.first()` snapshot. Define this read as the linearization point: mute/unmute writes completed before it affect the current sync; writes completed after it affect later syncs.
6. Compute `eligibleTopicIds = followedTopics - mutedTopics`, then intersect with active, fully populated topics.
7. Select only IDs in `changedIds - existingChangedIds`, load those rows in publish-date-descending order, retain rows whose fresh payload topic IDs intersect `eligibleTopicIds`, and call the notifier only if the result is non-empty. Room already orders candidate rows by publication date, and the notifier truncates that order to five (`core/database/src/main/kotlin/com/google/samples/apps/nowinandroid/core/database/dao/NewsResourceDao.kt:41-66`, `getNewsResources`; `core/notifications/src/main/kotlin/com/google/samples/apps/nowinandroid/core/notifications/SystemTrayNotifier.kt:40-69`, `MAX_NUM_NOTIFICATIONS` and truncation).

Specified edge behavior

- One muted followed topic only: no notification.
- Muted followed topic plus an unfollowed topic: no notification; the unmuted topic is not eligible because it is not followed.
- Muted followed topic plus another followed, unmuted topic: notify once. Eligibility is OR across eligible topic associations, matching the feed’s existing any-topic semantics (`core/database/src/main/kotlin/com/google/samples/apps/nowinandroid/core/database/dao/NewsResourceDao.kt:50-55`, topic subquery).
- Empty topic set: no notification. An empty payload association cannot intersect eligible topics (`core/network/src/main/kotlin/com/google/samples/apps/nowinandroid/core/network/model/NetworkNewsResource.kt:37-38`, default `topics`).
- Removed topic: retain the muted ID in user preferences so stale associations remain suppressed. Exclude topic shells/unresolved topic IDs from `activeTopicIds`; shells are identifiable at this revision because synchronization creates them with blank metadata (`core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/model/NewsResource.kt:37-51`, `NetworkNewsResource.topicEntityShells`). Topic deletion cascades existing cross-references (`core/database/src/main/kotlin/com/google/samples/apps/nowinandroid/core/database/model/NewsResourceTopicCrossRef.kt:27-43`, `NewsResourceTopicCrossRef` foreign keys).
- To make the active-topic check deterministic, change `SyncWorker` from parallel topic/news sync to topic sync first and news sync second. Current parallelism allows news synchronization to create a shell concurrently with topic deletion (`sync/work/src/main/kotlin/com/google/samples/apps/nowinandroid/sync/workers/SyncWorker.kt:72-76`, `SyncWorker.doWork`; `core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/repository/OfflineFirstTopicsRepository.kt:49-64`, `OfflineFirstTopicsRepository.syncWith`).
- Repeat sync: the change-list version normally prevents reprocessing; if a crash occurs after database upsert but before version advancement, the ID-only existence check suppresses a duplicate on retry. Version advancement currently occurs after `modelUpdater` (`core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/SyncUtilities.kt:91-103`, `changeListSync`).
- Stale local relationships: use `freshTopicIdsByNewsId` for notification eligibility and replace stored cross-references. Do not decide eligibility from the possibly stale `PopulatedNewsResource.topics` alone; current synchronization only inserts/ignores references (`core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/repository/OfflineFirstNewsRepository.kt:102-125`, network upsert path).
- Never pass an empty list to `SystemTrayNotifier`; otherwise its implementation would still construct a zero-item summary. Preserve the repository’s current non-empty guard (`core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/repository/OfflineFirstNewsRepository.kt:137-141`, notifier guard).

9. Failure modes and minimal implementation order

Important failure modes

- Accidentally deriving feed topics from `followedTopics - mutedTopics` would violate the central requirement; the feed must continue observing `followedTopics` unchanged (`core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/repository/CompositeUserNewsResourceRepository.kt:52-58`, `observeAllForFollowedTopics`).
- Clearing mute on unfollow would make the two controls coupled and would silently lose a user choice.
- Filtering only with the pre-sync followed-topic DAO query can misclassify changed existing news as new (`core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/repository/OfflineFirstNewsRepository.kt:83-94`, current existing-ID query).
- Appending cross-references leaves stale topic eligibility (`core/database/src/main/kotlin/com/google/samples/apps/nowinandroid/core/database/dao/NewsResourceDao.kt:105-108`, `insertOrIgnoreTopicCrossRefEntities`).
- Parallel topic/news sync makes removed-topic eligibility nondeterministic because news sync creates blank shells while topic sync deletes/upserts catalog rows (`sync/work/src/main/kotlin/com/google/samples/apps/nowinandroid/sync/workers/SyncWorker.kt:72-76`, parallel sync; `core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/model/NewsResource.kt:37-51`, shell creation).
- Restored user preferences plus an empty database can produce historical first-sync notifications under current logic despite marking items viewed (`core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/repository/OfflineFirstNewsRepository.kt:96-100`, first-sync viewed marking; `core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/repository/OfflineFirstNewsRepository.kt:127-141`, notification path).
- A mute occurring after the final user-data snapshot cannot retract a notification already being posted. Document the final snapshot as the operation’s linearization point; avoid claiming stronger cross-coroutine atomicity.
- Removed IDs can persist indefinitely. Showing unresolved entries in settings keeps them manageable without inventing remote cleanup.

Minimal ordered implementation sequence

1. Add the proto field and model default mapping; add serializer compatibility tests.
2. Add DataStore and repository mute mutations plus analytics; update all fakes/default fixtures and repository tests.
3. Add the For You regression test before notification work.
4. Add DAO cross-reference replacement and integration tests.
5. Serialize topic sync before news sync and test worker ordering.
6. Refactor notification novelty detection, fresh association capture, first-sync suppression, active-topic filtering, and edge-case tests.
7. Add topic view-model state/event, UI control, strings, semantics, and tests.
8. Add settings topic combination, unresolved-item representation, unmute UI, strings, semantics, and tests.
9. Run focused module tests, database instrumentation tests, worker tests, Compose UI tests, then the relevant demo/prod compilation variants. The flavor distinction must remain only at the current notifier/network bindings, not in mute persistence or filtering (`core/notifications/src/demo/kotlin/com/google/samples/apps/nowinandroid/core/notifications/NotificationsModule.kt:24-31`, demo notifier binding; `core/notifications/src/prod/kotlin/com/google/samples/apps/nowinandroid/core/notifications/NotificationsModule.kt:24-31`, prod notifier binding).
