1. Current ownership and data flow

Verified current behavior

User data and following

- `UserData` contains bookmarks, viewed news, followed topic IDs, appearance preferences, and onboarding state; it has no notification or mute state today (`core/model/src/main/kotlin/com/google/samples/apps/nowinandroid/core/model/data/UserData.kt:22-30`, `UserData`).
- Those values are stored in protobuf DataStore. Set-like preferences are represented as `map<string,bool>` whose keys carry the actual state; followed topics use field 13, bookmarks field 15, and viewed news field 20 (`core/datastore-proto/src/main/proto/com/google/samples/apps/nowinandroid/data/user_preferences.proto:25-53`, `UserPreferences`).
- `NiaPreferencesDataSource.userData` maps protobuf map keys into `UserData` sets, and `setTopicIdFollowed` independently inserts or removes one followed-topic key (`core/datastore/src/main/kotlin/com/google/samples/apps/nowinandroid/core/datastore/NiaPreferencesDataSource.kt:32-60`, `userData`; `core/datastore/src/main/kotlin/com/google/samples/apps/nowinandroid/core/datastore/NiaPreferencesDataSource.kt:76-91`, `setTopicIdFollowed`).
- `OfflineFirstUserDataRepository` merely exposes that local flow and delegates follow mutations to DataStore, adding analytics afterward (`core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/repository/OfflineFirstUserDataRepository.kt:33-43`, `userData`, `setTopicIdFollowed`).
- Hilt binds this implementation globally; there is not a flavor-specific user-data repository (`core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/di/DataModule.kt:52-55`, `bindsUserDataRepository`).

There is no remote user-data synchronization

- `NiaNetworkDataSource` has only topics, news resources, and their change lists (`core/network/src/main/kotlin/com/google/samples/apps/nowinandroid/core/network/NiaNetworkDataSource.kt:26-34`, `NiaNetworkDataSource`).
- The production Retrofit API declares GET endpoints only for topics, news, and change lists; it has no user-preference request (`core/network/src/main/kotlin/com/google/samples/apps/nowinandroid/core/network/retrofit/RetrofitNiaNetwork.kt:39-59`, `RetrofitNiaNetworkApi`).
- Therefore muting should remain local user data. Adding a fictitious remote preference endpoint or user-data sync worker would not fit this revision.

For You feed

- `CompositeUserNewsResourceRepository.observeAllForFollowedTopics` observes only `UserData.followedTopics`, then queries news associated with those IDs (`core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/repository/CompositeUserNewsResourceRepository.kt:52-59`, `observeAllForFollowedTopics`).

- This is the key invariant to preserve: muting must not alter `followedTopics`, and `observeAllForFollowedTopics` must remain mute-blind.

Topic/domain state

- `GetFollowableTopicsUseCase` maps a topic to `FollowableTopic` solely by testing membership in `userData.followedTopics` (`core/domain/src/main/kotlin/com/google/samples/apps/nowinandroid/core/domain/GetFollowableTopicsUseCase.kt:40-55`, `invoke`).

Sync and notification ownership

2. Model, persistence, migration, and backup

Proposed design

Protobuf

Add the next available protobuf field:

- `map<string, bool> muted_topic_ids = 21;`

Field 21 is explicitly the next available number (`core/datastore-proto/src/main/proto/com/google/samples/apps/nowinandroid/data/user_preferences.proto:25-53`, `UserPreferences`).

Use the same map-as-set convention as followed topics:

- muting inserts `topicId -> true`;
- unmuting removes the key;
- consumers use `mutedTopicIdsMap.keys`;
- do not interpret stored `false` as meaningful because the schema comment says map values have no meaning (`core/datastore-proto/src/main/proto/com/google/samples/apps/nowinandroid/data/user_preferences.proto:37-43`, `UserPreferences`).

Domain model and defaults

Add:

- `val mutedTopics: Set<String>`

to `UserData`, adjacent to `followedTopics` (`core/model/src/main/kotlin/com/google/samples/apps/nowinandroid/core/model/data/UserData.kt:22-30`, `UserData`).

The default must be `emptySet()`, meaning every existing user remains unmuted. Update all explicit constructors, especially `emptyUserData` (`core/testing/src/main/kotlin/com/google/samples/apps/nowinandroid/core/testing/repository/TestUserDataRepository.kt:28-36`, `emptyUserData`).

Schema evolution

No custom `DataMigration` and no Room version change are required:

- Proto3 treats an absent new map field as an empty map.
- `UserPreferencesSerializer` parses protobuf directly and uses `getDefaultInstance()` for new storage (`core/datastore/src/main/kotlin/com/google/samples/apps/nowinandroid/core/datastore/UserPreferencesSerializer.kt:29-44`, `UserPreferencesSerializer`).
- The preference does not belong in the Room database; Room currently owns downloaded topics/news and relations, not user preferences (`core/database/src/main/kotlin/com/google/samples/apps/nowinandroid/core/database/NiaDatabase.kt:36-72`, `NiaDatabase`).
- Do not add field 21 to the `reserved` list; if the field is removed in a later release, reserve it then.

The existing DataStore module explicitly registers only `IntToStringIdsMigration`; the older `ListToMapMigration` exists but is not registered in the current provider (`core/datastore/src/main/kotlin/com/google/samples/apps/nowinandroid/core/datastore/di/DataStoreModule.kt:42-58`, `providesUserPreferencesDataStore`; `core/datastore/src/main/kotlin/com/google/samples/apps/nowinandroid/core/datastore/ListToMapMigration.kt:24-57`, `ListToMapMigration`). The new additive field should not alter that unrelated historical behavior.

Migration compatibility test

Add a serializer compatibility test that parses bytes generated without field 21 and verifies:

- existing followed/bookmarked/appearance values survive;
- `mutedTopics` is empty;
- writing and reparsing after setting muted IDs preserves them.

That verifies the actual migration mechanism—protobuf backward compatibility—rather than inventing a DataMigration.

Backup and restore

- The app opts into Android backup with `android:allowBackup="true"` and the inspected `<application>` declaration contains neither `dataExtractionRules` nor `fullBackupContent` (`app/src/main/AndroidManifest.xml:31-71`, `application`).
- Keep mute state in the existing `user_preferences.pb` DataStore file (`core/datastore/src/main/kotlin/com/google/samples/apps/nowinandroid/core/datastore/di/DataStoreModule.kt:42-58`, `providesUserPreferencesDataStore`). That gives it the same backup/restore behavior as followed topics and bookmarks.
- Do not add a backup exclusion solely for mute state.
- A restored preference can precede restoration or synchronization of topic metadata. Never erase unresolved muted IDs merely because `TopicsRepository.getTopics()` is temporarily empty. Settings should expose unresolved IDs through a fallback row so users can still unmute them.

4. Notification filtering boundary and edge behavior

Correct boundary

Filter in `OfflineFirstNewsRepository.syncWith`, immediately before constructing `addedNewsResources` and invoking `Notifier` (`core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/repository/OfflineFirstNewsRepository.kt:66-145`, `syncWith`).

Do not filter in `SystemTrayNotifier`:

- it should remain a presentation adapter;
- demo and prod then share identical eligibility behavior;
- tests can inspect the notifier input without Android notification machinery;
- a future notifier implementation cannot accidentally bypass mute policy (`core/notifications/src/main/kotlin/com/google/samples/apps/nowinandroid/core/notifications/Notifier.kt:24-26`, `Notifier`).

Exact eligibility rule

For a genuinely new synchronized resource `r`:

`eligible(r) = r.topics.any { it in followedTopics && it !in mutedTopics }`

Consequences:

- Only muted followed topics: suppress.
- Mixed muted and unmuted followed topics: notify once.
- A muted topic plus an unfollowed unmuted topic: suppress.
- Empty topic set: suppress.
- Empty `followedTopics - mutedTopics`: suppress without issuing a topic-filtered DAO query or calling `Notifier`.
- Muting does not mark the resource viewed, bookmark it, remove it, or alter its feed membership.

Newness and repeat sync

The current baseline query finds only existing resources that already match followed topics (`core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/repository/OfflineFirstNewsRepository.kt:83-97`, `syncWith`). Replace this with an unqualified pre-upsert lookup of all changed IDs:

- `existingChangedIds = getNewsResourceIds(filterNewsIds = changedIds)`
- `newIds = changedIds - existingChangedIds`

This prevents an old stored resource from becoming “new” merely because the user unmutes/follows a topic or because topic associations change.

`changeListSync` advances its version after the updater (`core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/SyncUtilities.kt:94-104`, `changeListSync`), while the preexisting-ID check makes retries idempotent: once an item was inserted, a retry will not notify it again.

Stale user-data race

The current code reads `userData` before downloading/upserting news (`core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/repository/OfflineFirstNewsRepository.kt:79-82`, `syncWith`). Re-read `NiaPreferencesDataSource.userData.first()` after the upserts and immediately before filtering. This ensures a mute made while a long sync is running is honored before any user-facing notification is posted.

Stale topic relations

`NetworkNewsResource` carries the authoritative topic-ID list for the fetched representation (`core/network/src/main/kotlin/com/google/samples/apps/nowinandroid/core/network/model/NetworkNewsResource.kt:27-38`, `NetworkNewsResource`).

The Room sync currently only inserts cross-references with `IGNORE`; it does not replace removed relations (`core/database/src/main/kotlin/com/google/samples/apps/nowinandroid/core/database/dao/NewsResourceDao.kt:105-108`, `insertOrIgnoreTopicCrossRefEntities`). Therefore:

- collect the fetched `NetworkNewsResource` objects across sync batches;
- evaluate notification eligibility against their fresh `topics` lists;
- use Room only to materialize the final eligible `newIds` into `NewsResource` objects for `Notifier`.

This prevents stale Room cross-references from causing a muted-only resource to notify.

Deleted and unresolved topics

- Topic deletion cascades its current cross-references (`core/database/src/main/kotlin/com/google/samples/apps/nowinandroid/core/database/model/NewsResourceTopicCrossRef.kt:27-54`, `NewsResourceTopicCrossRef`; `core/database/src/main/kotlin/com/google/samples/apps/nowinandroid/core/database/dao/TopicDao.kt:69-75`, `deleteTopics`).
- Do not automatically prune mute IDs when a topic is deleted. A prune based on the local topic table could destroy restored preferences before synchronization.
- If a deleted topic later reappears under the same ID, its prior mute remains effective.
- A fetched resource is evaluated only from its fresh network topic IDs. An unresolved muted ID still suppresses that association.
- Settings should retain an explicit “Unavailable topic” row keyed by ID so a stale preference remains removable.

First sync

Current code marks first-sync news viewed but can still post notifications when restored user data says onboarding is complete (`core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/repository/OfflineFirstNewsRepository.kt:99-104`, `syncWith`). Historical first-sync content is not “newly synchronized news” from the user’s perspective. Gate notification posting with `hasOnboarded && !isFirstSync`; continue marking all first-sync IDs viewed.

9. Failure modes and ordered implementation

Important failure modes

1. Reusing `setTopicIdFollowed` for mute would silently unfollow topics and remove feed items.
2. Filtering in `SystemTrayNotifier` would leave policy flavor/implementation-dependent.
3. Subtracting muted IDs from the For You query would violate the central requirement.
4. Reading preferences only at sync start can post after a user muted during the fetch.
5. Filtering with insert-only Room cross-references can use obsolete topic associations.
6. Treating all changed IDs as new can notify old resources after unmute/follow changes.
7. Calling the notifier with an empty list can create an empty summary notification; `SystemTrayNotifier` currently always constructs a summary after permission succeeds (`core/notifications/src/main/kotlin/com/google/samples/apps/nowinandroid/core/notifications/SystemTrayNotifier.kt:60-104`, `postNewsNotifications`).
8. Pruning IDs against an empty or partially restored topic table can lose backup-restored preferences.
9. Hiding unresolved muted IDs makes them impossible to manage from settings.
10. Logging analytics after a swallowed DataStore failure records a state that was never saved.
11. Not suppressing first-sync notifications can surface historical content after restore.
12. Adding a Room column/table would create unnecessary migration and backup complexity for what is already local protobuf user data.

Minimal ordered sequence

1. Add protobuf field 21, `UserData.mutedTopics`, defaults, constructors, and test-double support.
2. Add DataStore mapping/mutations and wire-compatibility/default/independence tests.
3. Add repository APIs and repository-level analytics with success-sensitive logging.
4. Refactor notification newness detection and add the complete filtering matrix before touching UI.
5. Add topic-state derivation, view-model mutation, independent accessible control, strings, and tests.
6. Add settings topic resolution, unresolved fallback rows, unmute event, UI strings, and tests.
7. Run feed-regression tests to prove muting does not affect `observeAllForFollowedTopics`.
8. Run demo/prod compilation and the relevant unit/instrumented suites.
9. Perform explicit backup/restore verification on a device or managed device.
