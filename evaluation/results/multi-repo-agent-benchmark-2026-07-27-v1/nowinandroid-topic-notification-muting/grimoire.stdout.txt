Verified scope: the concrete user-preference model/datastore/repository chain, followed-topic feed path, topic and settings feature implementations, news synchronization and notifier boundary, shared test doubles, and flavor-specific network/sync entry points. “Current” below describes this revision; “Proposed” describes the implementation design.

1. Current ownership and data-flow map

User data and followed topics

- `UserData` is the in-memory user-preference model. It currently carries `followedTopics` with theme, dynamic-color, and onboarding preferences; there is no mute state. `core/model/src/main/kotlin/com/google/samples/apps/nowinandroid/core/model/data/UserData.kt:22-31` (`UserData`).
- The durable schema is the protobuf `UserPreferences`. Followed string IDs occupy field 5; fields through 9 are already assigned, while field 2 is reserved. `core/datastore-proto/src/main/proto/com/google/samples/apps/nowinandroid/data/user_preferences.proto:25-38` (`UserPreferences`).
- `NiaPreferencesDataSource.userData` maps protobuf preferences into `UserData`, and its followed-topic mutators use DataStore `updateData`, providing local, transactional, offline-capable writes. `core/datastore/src/main/kotlin/com/google/samples/apps/nowinandroid/core/datastore/NiaPreferencesDataSource.kt:41-74` (`userData`, `setFollowedTopicIds`, `toggleFollowedTopicId`).
- `UserDataRepository` is the domain-facing owner of the preference flow and mutation API. `OfflineFirstUserDataRepository` forwards these operations to `NiaPreferencesDataSource`; it does not invoke a user account or remote user-data service. This revision therefore has local user-data persistence, not remote user-data synchronization. `core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/repository/UserDataRepository.kt:24-46` (`UserDataRepository`); `core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/repository/OfflineFirstUserDataRepository.kt:27-55` (`OfflineFirstUserDataRepository`).

Feed

- Followed topics are combined with locally stored news to produce user news resources. Mute must not enter this query or the resulting feed mapping. `core/domain/src/main/kotlin/com/google/samples/apps/nowinandroid/core/domain/GetUserNewsResourcesUseCase.kt:33-70` (`GetUserNewsResourcesUseCase`).
- `NewsResourceQuery.filterTopicIds` is the existing topic-selection mechanism in the news repository. Keeping it based on `UserData.followedTopics` is what preserves muted topics in For You. `core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/repository/NewsRepository.kt:25-42` (`NewsResourceQuery`, `NewsRepository.getNewsResources`).

Topic UI

- `TopicViewModel.followTopicToggle` is the current topic-screen mutation entry point. `topicUiState` combines the topic and user data into `TopicUiState.Success`. `feature/topic/impl/src/main/kotlin/com/google/samples/apps/nowinandroid/feature/topic/impl/TopicViewModel.kt:55-102` (`TopicViewModel`, `followTopicToggle`, `topicUiState`).
- `TopicUiState.Success` currently exposes a `FollowableTopic`, so it represents follow state but not an independent notification state. `feature/topic/impl/src/main/kotlin/com/google/samples/apps/nowinandroid/feature/topic/impl/TopicViewModel.kt:161-169` (`TopicUiState.Success`).

Synchronization and notifications

- `OfflineFirstNewsRepository.syncWith` owns ingestion of network news and topic cross-references into local storage. It supplies synchronized news resources to the notification abstraction rather than constructing Android notifications itself. `core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/repository/OfflineFirstNewsRepository.kt:48-145` (`OfflineFirstNewsRepository.syncWith`).
- `Notifier.postNewsNotifications` accepts domain `NewsResource` objects. 2. Model, persistence, migration, and backup

Proposed model

- Add `val mutedTopicIds: Set<String>` to `UserData`, adjacent to `followedTopics`, with `emptySet()` supplied by every production/test fixture. The two sets must remain independent; neither is derived from the other. The insertion point is `core/model/src/main/kotlin/com/google/samples/apps/nowinandroid/core/model/data/UserData.kt:22-31` (`UserData`).
- Add `repeated string muted_topic_ids = 10;` to `UserPreferences`. Ten is the next unused field after `should_hide_onboarding = 9`; do not reuse reserved field 2 or renumber existing fields. `core/datastore-proto/src/main/proto/com/google/samples/apps/nowinandroid/data/user_preferences.proto:25-38` (`UserPreferences`).

Defaults and schema evolution

- Protobuf’s absent repeated-field default is an empty list, which maps to `emptySet()`. Existing installs consequently begin with no muted topics.
- This is not a Room schema change. Do not bump `NiaDatabase` or add a Room migration. The only serialized schema changing is the DataStore protobuf.
- No custom DataStore `DataMigration` is needed for valid old protobuf files: parsing old bytes yields an empty `mutedTopicIdsList`. The existing legacy integer-to-string followed-topic migration remains untouched and should produce an empty muted set because legacy storage contains no mute concept. `core/datastore/src/main/kotlin/com/google/samples/apps/nowinandroid/core/datastore/IntToStringIdsMigration.kt:24-57` (`IntToStringIdsMigration`).

Datastore changes

- Extend `NiaPreferencesDataSource.userData` with `mutedTopicIds = mutedTopicIdsList.toSet()`.
- Add:
  - `suspend fun setMutedTopicIds(topicIds: Set<String>)`
  - `suspend fun setTopicIdMuted(topicId: String, muted: Boolean)`
- Implement both through one `updateData` transaction and protobuf `clearMutedTopicIds()/addAllMutedTopicIds(...)`, mirroring followed-topic persistence. `core/datastore/src/main/kotlin/com/google/samples/apps/nowinandroid/core/datastore/NiaPreferencesDataSource.kt:41-89` (`userData`, followed-topic mutators).
- Do not alter mute state in `setTopicIdFollowed`. Unfollowing and refollowing therefore preserves mute state, which is the strongest interpretation of independent choices. Muting never unfollows a topic.

Backup

- The value remains inside the existing user-preferences DataStore file, so backup/restore naturally treats follow and mute as one atomic preference artifact. No new database or standalone file should be introduced.
- Keep the existing app backup declarations and rules unchanged unless implementation verification discovers that the current DataStore directory is explicitly excluded. The app already delegates backup selection to its XML rules. `app/src/main/AndroidManifest.xml:29-38` (`application` backup attributes); `app/src/main/res/xml/backup_rules.xml:18-25` (`full-backup-content`); `app/src/main/res/xml/data_extraction_rules.xml:18-29` (`data-extraction-rules`).
- Add a restore-style serialization test: write preferences containing followed and muted sets, recreate the DataStore, and assert both survive. Also parse a pre-field-10 fixture and assert mute defaults empty.

Proposed repository API

Add to `UserDataRepository`:

- `val userData: Flow<UserData>` remains the read API.
- `suspend fun setTopicIdMuted(topicId: String, muted: Boolean)`.
- Optionally `suspend fun setMutedTopicIds(topicIds: Set<String>)` if bulk replacement is needed by settings; individual unmute does not require it.

`OfflineFirstUserDataRepository` should delegate directly to the datastore, just as it does for follow state. Independence contract

- `setTopicIdFollowed(id, false)` changes only `followedTopics`.
- `setTopicIdMuted(id, true)` changes only `mutedTopicIds`.
- Muting a followed topic leaves it followed.
- A muted-but-unfollowed ID is permitted. It has no immediate notification effect, but refollowing remains muted.
- For You continues to receive only `followedTopics`; never subtract `mutedTopicIds` in `GetUserNewsResourcesUseCase` or `NewsResourceQuery`. `core/domain/src/main/kotlin/com/google/samples/apps/nowinandroid/core/domain/GetUserNewsResourcesUseCase.kt:33-70` (`GetUserNewsResourcesUseCase`).

Settings domain state

Introduce a small `GetMutedTopicsUseCase` in `core/domain` that combines:

- `UserDataRepository.userData`
- `TopicsRepository.getTopics()`

Return entries for every persisted muted ID:

- `Available(topic: Topic)` when the topic still exists locally.
- `Unavailable(topicId: String)` when it does not.

This lets settings unmute removed/stale IDs instead of silently making them unmanageable. `core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/repository/TopicsRepository.kt:24-38` (`TopicsRepository`); `core/model/src/main/kotlin/com/google/samples/apps/nowinandroid/core/model/data/Topic.kt:22-29` (`Topic`).

4. Notification-filtering boundary and edge behavior

Exact proposed boundary

Apply the policy in `SystemTrayNotifier.postNewsNotifications`, immediately after sampling `userDataRepository.userData.first()` and before notification grouping/building. Do not filter in:

- `OfflineFirstNewsRepository`, because synchronization should persist all news regardless of notification preferences.
- `Notifier`’s interface, because it should continue accepting synchronized candidate resources.
- `NewsResourceQuery`, because that would risk changing For You.
- `SyncWorker`, because it does not own topic/user eligibility.

This preserves the established ownership split at `core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/repository/OfflineFirstNewsRepository.kt:48-145` (`syncWith`), `core/notifications/src/main/kotlin/com/google/samples/apps/nowinandroid/core/notifications/Notifier.kt:24-25` (`postNewsNotifications`), and `core/notifications/src/main/kotlin/com/google/samples/apps/nowinandroid/core/notifications/SystemTrayNotifier.kt:48-112` (`postNewsNotifications`).

Eligibility formula

For each synchronized candidate:

`eligibleTopicIds = news.topicIds ∩ (followedTopicIds - mutedTopicIds)`

Post the news resource iff `eligibleTopicIds` is non-empty.

Required cases:

- Only muted topics: no notification.
- One muted followed topic plus one unmuted followed topic: notify once.
- Muted followed topic plus unmuted but unfollowed topic: no notification.
- Multiple unmuted followed topics: still one news notification, not one per topic.
- Empty topic set: no notification. This is a fail-closed policy and avoids topicless or incompletely joined data bypassing preferences.
- Removed topic:
  - Keep its muted ID in DataStore.
  - If the synchronized news still exposes that topic ID, it remains muted.
  - If the local relation has disappeared and the resource exposes no topics, the empty-set rule suppresses notification.
  - If the topic later returns with the same ID, the retained mute immediately applies.
- Repeat sync with no new change-list entries: no candidate is forwarded, so no repost.
- If a later server revision marks the same news item changed, it is a new synchronized candidate under current change-list behavior and may be reconsidered. Muting does not provide per-news deduplication; introducing such deduplication would be a separate persistence feature.
- Stale user state: sample the latest DataStore value as late as possible, in the notifier, after news persistence. A mute write that completed before this sample must be honored. A concurrently in-flight write can race; do not cache `UserData` in the notifier.
- Stale topic relations: filter the locally reconstructed synchronized `NewsResource`, not the earlier network DTO, so notification content and eligibility use the same committed local representation. `core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/repository/OfflineFirstNewsRepository.kt:90-145` (`syncWith`).

First synchronization should retain the existing suppression behavior; mute filtering is applied only when the current pipeline elects to notify, not as a reason to change first-sync semantics. `core/data/src/main/kotlin/com/google/samples/apps/nowinandroid/core/data/repository/OfflineFirstNewsRepository.kt:90-145` (`syncWith`).

9. Failure modes and ordered implementation sequence

Important failure modes

- Accidentally subtracting muted IDs from `NewsResourceQuery` removes muted content from For You. Keep mute out of feed selection.
- Making muted IDs a subset of followed IDs couples the toggles and loses the user’s preference on unfollow/refollow.
- Reusing a protobuf field number can corrupt compatibility. Use field 10 and retain existing/reserved numbers.
- Adding a Room migration is unnecessary and risks unrelated database churn.
- Filtering network DTOs before local persistence can disagree with the topic relations used to display the notification.
- Treating “any muted topic” as suppressing a multi-topic item is too broad. Suppress only when there is no unmuted followed association.
- Treating an empty/missing topic set as eligible leaks notifications through incomplete data; fail closed.
- Removing stale muted IDs automatically makes a reintroduced topic noisy and prevents settings from managing the choice. Preserve the ID and expose an unavailable entry.
- Caching `UserData` in the notifier can ignore a recently completed mute.
- Implementing mute through prod FCM subscriptions would invent remote synchronization, diverge from demo, and fail offline.
- Updating production interfaces without test repositories and `UserData` fixtures will cause widespread compile failures.

Minimal ordered sequence

1. Add protobuf field 10 and `UserData.mutedTopicIds`; update generated protobuf output through the normal build only during implementation.
2. Extend datastore mapping/mutators and write compatibility, persistence, and backup-style tests.
3. Extend `UserDataRepository`, `OfflineFirstUserDataRepository`, test repositories, and canonical fixtures; verify follow/mute independence.
4. Implement and test `SystemTrayNotifier` eligibility using `followedTopics - mutedTopicIds`; add the complete edge-case matrix.
5. Add the For You regression test proving muted followed content remains eligible.
6. Extend topic view-model state/events, analytics, UI, strings, semantics, and tests.
7. Add `GetMutedTopicsUseCase`, including unavailable IDs.
8. Extend settings state/events/UI, analytics, accessibility, and tests.
9. Verify shared DI and both demo/prod variants, then run datastore, data, domain, notifications, topic, settings, sync, and variant-level test suites.
