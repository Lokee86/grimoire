2. Exact filtering boundary

Proposed boundary

Introduce recipient filtering inside the realtime world-projection seam, immediately before `BuildWorldFullPacket` is quantized and compared with the recipient’s stored baseline:

- Add a pure `visibility.Region`/`visibility.ContainsWithMargin` seam under `services/game-server/internal/game/visibility/`, extracted from the current wrap-aware helpers.
- Keep the current simulation helpers as delegates to that seam.
- Add `WorldInterestContext` and `ProjectInterestedWorldLane(snapshot, context, previousWorld)` in `services/game-server/internal/protocol/realtime/projection_world.go`.
- Change `buildWorldLaneCandidates` to construct the filtered `currentWorld` before `WorldWirePayloadChanged`, `BuildWorldWireDeltaPacket`, lifecycle splitting, and hot-lane projection.
- Pass a receiver `PresentationView` into `BuildActiveRealtimeResultForGame`; it should contain the validated view config, resolved authoritative anchor, receiver ID, and resolved spectate target ID.

This is the exact boundary because:

- The immutable simulation frame should remain complete and globally authoritative; it is currently published once for all recipients (`services/game-server/internal/game/presentation_snapshot.go:22-64`).
- Filtering in simulation would incorrectly make entity existence/outcomes dependent on who is observing. Current asteroid and bullet retention deliberately considers all cameras (`services/game-server/internal/game/visibility.go:62-88`).
- Filtering in WebRTC transport would occur after global candidate generation and after baseline comparison, so it could not produce correct recipient-specific creates/deletes (`services/game-server/internal/protocol/realtime/active.go:40-77`).
- Filtering after delta creation would omit movement bytes but would not reliably remove leaving entities from the client.
- Filtering before projection would allow separate sessions to reuse the same immutable snapshot while producing distinct world baselines, which the current receiver-scoped `RealtimeSessionState` already supports (`services/game-server/internal/protocol/realtime/baseline.go:27-45`).

Do not store speculative interest membership separately during candidate assembly. Derive the previous membership from the successfully committed `WorldWireFullPacket` baseline. This preserves the existing rule that state represents successfully delivered client state, not attempted state (`services/game-server/internal/protocol/realtime/baseline.go:152-187`).

3. Entity policy, hysteresis, self/spectate, and leaving interest

Proposed region policy

Add networking-specific generated constants rather than reusing asteroid-named constants:

- `network_interest_enter_margin = 160.0`
- `network_interest_exit_margin = 320.0`
- `player_locator_tick_interval = 6`

The initial margins intentionally match the proven spawn/despawn separation but remain independently tunable (`shared/constants/server_entities.toml:18-19`). At 60 Hz, six ticks gives a 10 Hz locator cadence (`shared/constants/server_constants.toml:2`).

For each entity center:

- Not in the successfully delivered baseline: include only if inside the camera rectangle plus the 160-unit enter margin.
- Already in the successfully delivered baseline: retain until outside the rectangle plus the 320-unit exit margin.
- Use wrap-aware `space.Delta`, not `CameraView.IsInside`, because `CameraView.IsInside` performs direct non-wrapped bounds comparisons (`services/game-server/internal/game/runtime/camera.go:54-66`) while the existing simulation helper is toroidal (`services/game-server/internal/game/visibility.go:94-109`).

Entity-class policy

- Ships:
  - Normal remote ship: enter/retain by region.
  - Receiver’s live ship: force include regardless of region.
  - Resolved spectate/view-target ship: force include regardless of region.
  - Include complete ship create/lifecycle state on entry, then only hot movement and changed reliable fields through existing lanes.
- Bullets:
  - Region policy only; do not force every projectile belonging to self or the target. A projectile far outside the viewed region has no presentation value.
  - Keep lifecycle create/delete reliable and movement hot/unreliable as now (`services/game-server/internal/protocol/realtime/lane_candidate_world.go:43-85`).
- Asteroids:
  - Region policy only; retain through the wider exit boundary.
  - Continue authoritative simulation until the existing all-camera despawn policy removes them (`services/game-server/internal/game/visibility.go:62-73`).
- Pickups:
  - Region policy only.
  - Keep them in the reliable world delta because they currently have no dedicated lifecycle/hot lane (`services/game-server/internal/protocol/realtime/lane_candidate_world.go:43-85`).
- Session, overlay, player lifecycle, match counters, and queued events:
  - Do not interest-filter these in the first implementation. They are not hot entity state. Events are already receiver-queued and drained only after successful delivery (`services/game-server/internal/game/presentation_snapshot.go:81-113`, `services/game-server/internal/networking/websocket_write.go:148-153`).

Self and spectate

Add separate control packets `set_view_target_request` and `clear_view_target_request`; do not reuse `set_target_player_request`, because that currently mutates authoritative weapon/selection targeting (`services/game-server/internal/networking/inbound/gameplay.go:36-43`).

The server should:

1. Accept only `target_kind = "player"`.
2. Verify the target is a current participant with lifecycle `active`.
3. Store the selected target in the coherent `SessionContext`, so a mid-build target change makes `sessionContextMatches` reject the stale projection (`services/game-server/internal/networking/session_context.go:5-15`, `services/game-server/internal/networking/websocket_write.go:75-76`).
4. Resolve anchor position from the target’s authoritative ship/locator, but retain the receiver’s validated viewport dimensions.
5. Fall back to the receiver’s ship/camera position if the target disappears or becomes non-active.
6. Force the receiver and resolved target into the ship projection.

The client spectate flow must become asynchronous: send the view-target request, keep a pending target, and call `focus_camera_on_player` only after that target’s forced world create arrives. Today `begin_spectating` assumes the node already exists and only enters spectate mode when synchronous focus succeeds (`client/scripts/gameplay/spectate/gameplay_spectate_flow.gd:44-54`).

Leaving-interest behavior

When an entity crosses the exit boundary:

1. It is absent from `currentWorld`.
2. `CompareLaneRecordFields` emits a delete against the successfully delivered prior projection (`services/game-server/internal/protocol/realtime/delta.go:128-134`).
3. Existing lifecycle builders route ship/asteroid/bullet deletes reliably; pickup deletes remain in the reliable world delta (`services/game-server/internal/protocol/realtime/lane_candidate_lifecycle.go:3-58`).
4. The reliable world/lifecycle write group must succeed before the current filtered projection is committed (`services/game-server/internal/networking/websocket_write.go:139-150`).
5. The client removes the entity and records its tombstone, protecting it from late unordered hot packets (`client/scripts/protocol/realtime/world_lane_applier.gd:202-212`, `client/scripts/protocol/realtime/world_lane_state.gd:215-228`).
6. On re-entry, the delivered baseline no longer contains the entity, so comparison emits a full create rather than a delta against hidden stale state.

If the delete group is blocked by backpressure, do not evict membership or baseline state. The next tick should regenerate the delete from the same delivered baseline.

4. Low-cadence offscreen-player locator

- Spectate targets are also currently enumerated from `world_ships`, filtered by session lifecycle (`client/scripts/gameplay/spectate/spectate_menu_state.gd:15-34`, `client/scripts/gameplay/spectate/spectate_menu_state.gd:44-57`).

Proposed locator record

Extend the reliable session lane with:

- `player_locators` for full/create records
- `player_locator_updates`
- `player_locator_deletes`

Record fields:

- `id`
- `x`
- `y`
- `team_id`

Do not include rotation, thrust, velocity, health, shields, target selection, weapon state, or other hot ship fields. Lifecycle remains canonical in `player_lifecycle`, avoiding a duplicate status source (`services/game-server/internal/protocol/realtime/projection_session.go:45-62`).

Source locator coordinates from the existing authoritative player-world-state rules: active ship position, otherwise retained camera/spawn position (`services/game-server/internal/game/player_world_state.go:11-33`). Keep locator membership for every current player session, but only show indicators and spectate eligibility for lifecycle `active`.

Cadence and membership

- Include current locator samples in every session full baseline.
- Sample positions every six write ticks, initially 10 Hz.
- Between samples, retain the last committed locator coordinates in the session projection so normal session-field changes do not accidentally turn the locator path back into 60 Hz.
- Reconcile locator membership immediately even off-cadence: add a newly joined player and delete a disconnected player without waiting six ticks.
- Because rooms are capped at eight players, the lane has a bounded record count (`services/game-server/internal/playerids/playerids.go:5-8`).
- Keep locators in the ordered, reliable session channel (`services/game-server/internal/networking/webrtc_transport.go:30-40`).

Add `player_locators` to `SessionLaneState`; full packets replace it and deltas merge/create/delete it beside existing session records (`client/scripts/protocol/realtime/session_lane_state.gd:8-26`).

Add a dedicated `PlayerLocatorSource` under `client/scripts/gameplay/presentation/`:

- It consumes decoded locator records, lifecycle state, and `self_id`.
- It filters to active remote players.
- It maps authoritative toroidal positions into the current view-anchor copy through `WorldSync.visual_position_for_server_position`, rather than creating player nodes (`client/scripts/world/world_sync.gd:250-255`).
- `GameplayPresentationFlow` uses it as the indicator position provider instead of `get_remote_player_visual_positions`.
- Indicator rendering itself remains unchanged; it already accepts arbitrary target-position dictionaries and removes indicators absent from the source (`client/scripts/gameplay/presentation/os_indicator_controller.gd:25-59`).
- Extend `SpectateMenuState` to enumerate active locator IDs instead of interested `world_ships`.

This keeps coarse global awareness separate from rendered/hot world membership.

5. Server lane, candidate, baseline, and budget changes

World lane and candidates

- Modify `BuildActiveRealtimeResultForGame` to resolve a receiver `PresentationView` and pass it into candidate assembly; current assembly starts from a receiver snapshot but has no view context (`services/game-server/internal/protocol/realtime/active.go:35-43`).
- Modify only the world candidate path to consume an interested projection. Overlay remains receiver-scoped, session remains global/low-cadence, and event handling remains unchanged (`services/game-server/internal/protocol/realtime/planner.go:13-38`).
- Filter before quantization and delta construction in `buildWorldLaneCandidates` (`services/game-server/internal/protocol/realtime/lane_candidate_world.go:12-35`).
- Preserve the current independent hot lane generation, but its current entity sets must be derived from the interested `currentWorld` (`services/game-server/internal/protocol/realtime/lane_candidate_world.go:88-150`).
- Do not reset the world baseline on ordinary target changes. A target switch should naturally produce reliable deletes for the old region and creates for the new region.

Baseline correctness

- Previous interest membership comes from `state.BaselineProjection(LaneWorld)`.
- Current filtered projection becomes the candidate projection.
- Only `CommitSuccessfulCandidate` may make it the next baseline (`services/game-server/internal/protocol/realtime/baseline.go:152-187`).
- Full-baseline/resync packets must also be filtered for the current receiver view; otherwise a reconnect would temporarily recreate the global world.
- A target change occurring while a packet is being built must invalidate that build through session-context matching before write (`services/game-server/internal/networking/websocket_write.go:75-76`).

Budget and prioritization

Verified current policy:

- Soft scheduling target is 500 bytes, warning is 800, hard cap is 1200 (`services/game-server/internal/protocol/realtime/size_estimate.go:3-8`).
- Full/world/session/lifecycle records are required; hot lanes are marked high-priority/supersedable, although real hot-lane chunks are currently always admitted by the scheduler (`services/game-server/internal/protocol/realtime/candidate_policy.go:3-43`, `services/game-server/internal/protocol/realtime/scheduler.go:41-59`).
- World full and lifecycle candidates are hard-cap chunked, but session packets are not currently handled by `expandHardCapCandidate` (`services/game-server/internal/protocol/realtime/realtime_hardcap_chunker.go:5-35`).
- Existing hot-lane defaults use 48-entity budgets and 800/1200/1500 byte thresholds (`services/game-server/internal/protocol/realtime/hot_lane_policy.go:3-26`).

Proposed policy:

1. Reliable deletes and creates remain required and may not be dropped to satisfy the soft target.
2. Self and spectated-target ship movement rank first.
3. Other interested ships rank next, then bullets, then asteroids; use wrapped distance to the view anchor with ID as a deterministic tie-break.
4. Apply this ordering before hot/lifecycle chunk formation so the first chunks contain the most presentation-critical state.
5. Do not commit the hot projection for an unsent/deferred chunk group.
6. Keep existing adaptive hot cadence and hard-cap chunking after interest reduction.
7. Measure the maximum eight-player session full/delta including locators. If encoded size can exceed 1200, extend `expandHardCapCandidate` and add a client session-full assembler before rollout; do not assume the eight-player bound is automatically safe.
8. Add diagnostics counters for considered, enter-included, hysteresis-retained, forced-self, forced-target, culled, and interest-exit records, plus locator records/bytes and enter/exit churn. Existing per-packet diagnostics already capture encoded size, hot counts, modes, and over-budget classification (`services/game-server/internal/protocol/realtime/candidate_diagnostics.go:3-29`, `services/game-server/internal/protocol/realtime/candidate_diagnostics.go:31-58`).

Failure modes to guard explicitly

- Boundary oscillation: two thresholds must use committed membership, not last attempted membership.
- World wrap: never use direct rectangular coordinates.
- Stale client viewport: server defaults/clamps it; never trust an arbitrary client region.
- Malicious view target: validate participant and active lifecycle; the client cannot request arbitrary coordinates.
- Target switch race: abort packets built for the prior coherent session context.
- Interest exit versus global destruction: both delete world state, but only global disconnect deletes session/locator membership.
- Death/respawn: lifecycle suppresses indicators while locator may retain the death-camera position.
- Reliable delete blocked by budget/backpressure: baseline and membership remain unchanged.
- Late unordered hot packet after delete: tombstone prevents resurrection.
- Reconnect/resync: filtered full baseline, not global full baseline.
- Locator staleness: remove on membership delete and suppress by lifecycle; optionally apply a multiple-cadence stale timeout for indicators.
- Session packet growth: measure actual compact size at eight players and add chunking if it crosses 1200 bytes.
- Event leakage/bandwidth: events remain unchanged deliberately; spatial event filtering is a separate semantic project because some distant events carry globally important lifecycle information.
