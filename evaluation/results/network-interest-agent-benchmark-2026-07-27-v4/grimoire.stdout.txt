2. Exact filtering boundary

Proposed boundary

Introduce receiver-specific filtering inside `services/game-server/internal/protocol/realtime`, between the complete immutable `GameplayPresentationSnapshot` and `BuildWorldFullPacket`/quantization:

1. `GameplayPresentationSnapshot` remains the complete, immutable game-facing DTO.
2. Networking supplies a receiver projection context containing the requested view target.
3. Realtime projection resolves the authoritative view anchor and calculates an interested `WorldLaneProjection`.
4. Only that filtered projection is quantized and passed through the existing full/delta/lifecycle/hot pipeline.

Concretely, change `buildWorldLaneCandidates` so its current `BuildWorldFullPacket(snapshot, worldSequence)` step becomes something equivalent to:

- resolve `InterestView` from receiver camera config, receiver fallback position, and valid view target;
- obtain the previous committed `WorldWireFullPacket`;
- call a new `ProjectInterestedWorldLane(snapshot, interestView, previousWorld)`;
- build and quantize the world packet from that projection.

The insertion point is the existing `buildWorldLaneCandidates` construction boundary (`services/game-server/internal/protocol/realtime/lane_candidate_world.go:9-35`), while the reusable record construction remains adjacent to `ProjectWorldLane` (`services/game-server/internal/protocol/realtime/projection_world.go:16-108`).

Why this belongs in projection, not simulation

- Filtering must be receiver-specific, while the published frame is intentionally shared and immutable across all receivers (`services/game-server/internal/game/presentation_snapshot.go:9-20,81-113`).
- Simulation cameras currently affect authoritative spawn and cleanup policy. Repointing `game.cameraViews[playerID]` to a spectated target would let a presentation choice alter asteroid spawning and entity retention, violating the simulation/networking separation (`services/game-server/internal/game/visibility.go:52-88`, `services/game-server/internal/game/simulation_players.go:22-27`).
- The protocol layer already owns receiver-specific baselines, candidate construction, prioritization, chunking, and successful-write projection commits (`services/game-server/internal/protocol/realtime/baseline.go:27-45,83-99,152-187`, `services/game-server/internal/protocol/realtime/planner.go:13-38`).
- Therefore, keep simulation’s complete entity store and camera views unchanged. Copy only the receiver’s clamped camera dimensions and fallback camera position into the snapshot or a small game-facing `PresentationView` DTO. Do not expose mutable `runtime.CameraView` pointers to realtime projection.

Visibility seam reuse

Proposed: extract a generic wrapped rectangle primitive into `internal/game/space`, for example `InsideViewRect(center, position, halfWidth, halfHeight, margin)`. Make current simulation helpers and the new projection policy call it. This reuses the exact toroidal calculation instead of duplicating it; `space` already owns shortest wrapped deltas (`services/game-server/internal/game/space/space.go:29-38,67-80`) and the current visibility implementation is a direct wrapped rectangle comparison (`services/game-server/internal/game/visibility.go:94-109`).

3. Entity policy, hysteresis, self/spectate, and leaving interest

Interest rectangles

Proposed generated server tunables:

- `interest_enter_margin = 160`
- `interest_exit_margin = 320`
- `player_locator_interval_ticks = 6` at the current 60 Hz tick rate

Use new network-interest names rather than reusing asteroid constants semantically. The initial values intentionally align with the existing 160-unit spawn clearance and 320-unit retention margin, which are established viewport-scale cushions (`shared/constants/server_entities.toml:15-21`, `shared/constants/server_constants.toml:1-5`).

Membership rule:

- If an entity was not in the receiver’s last committed world projection, admit it when inside viewport plus `interest_enter_margin`.
- If it was in that committed projection, retain it until it is outside viewport plus `interest_exit_margin`.
- Always use wrapped deltas.
- Treat exact boundaries consistently with the existing inclusive viewport check; tests should lock down equality behavior (`services/game-server/internal/game/visibility.go:94-103`, `services/game-server/internal/game/visibility_test.go:26-39`).

The previous committed projection should be the hysteresis memory. Do not add an independently advancing membership cache. The session already stores exactly the projection successfully delivered to that receiver (`services/game-server/internal/protocol/realtime/baseline.go:83-99,152-170`). This avoids divergence when a reliable world/lifecycle send is backpressured.

Entity-class policy

- Ships:
  - Include spatially interested ships.
  - Force the receiver’s own active ship.
  - Force the resolved spectated/view-target ship.
  - Keep global score, lives, loadout, and lifecycle in the session lane; do not duplicate those fields into locator or hot movement.
  - Current world ship records contain both hot movement and reliable ship meaning, while session records already carry durable player/session data (`services/game-server/internal/protocol/realtime/records.go:5-17,65-77`, `services/game-server/internal/protocol/realtime/projection_session.go:20-63`).

- Asteroids:
  - Include only by enter/exit region.
  - Preserve pending-despawn presentation only while still in the interest region; simulation still owns actual destruction and removal.
  - Current asteroid lifecycle already separates create/delete from hot X/Y updates (`services/game-server/internal/protocol/realtime/lane_candidate_lifecycle.go:43-58`, `services/game-server/internal/protocol/realtime/hot_lane_projection.go:29-39`).

- Bullets:
  - Include only by enter/exit region.
  - Use the same initial margins, but keep the policy per-class so measurement can justify a larger bullet prefetch margin later.
  - Bullet lifecycle and movement are already independent, allowing the policy to filter membership without changing authoritative bullet simulation (`services/game-server/internal/protocol/realtime/lane_candidate_lifecycle.go:26-41`, `services/game-server/internal/protocol/realtime/hot_lane_projection.go:41-52`).

- Pickups:
  - Include by enter/exit region.
  - Their current creates, updates, and deletes remain on the reliable world lane because no pickup hot lane exists (`services/game-server/internal/protocol/realtime/projection_world.go:81-107`, `services/game-server/internal/protocol/realtime/delta.go:270-273`).

- Session, lifecycle status, receiver overlay, and match totals:
  - Do not interest-filter them. They are low-volume player/match meaning and are needed for HUD, respawn, menus, and spectate eligibility (`services/game-server/internal/protocol/realtime/projection_session.go:20-63`, `client/scripts/gameplay/spectate/spectate_menu_state.gd:15-57`).

Self and spectate rules

Proposed client-to-server contract: `view_target_request` with canonical `target_kind` + `target_id`, using `target_kind = "player"`. Do not use legacy `target_player_id`; the generic fields already exist on `ClientPacket` (`shared/packets/gameplay.toml:101-123`).

The target request is per connection, not game simulation state:

- Store it under the `webSocketSession` mutex alongside connection context.
- Add a narrow inbound session adapter method to set/clear it.
- Clear it whenever room/player/match identity changes.
- The write loop snapshots the requested target and passes it to realtime projection.
- This follows the existing split where inbound routing adapts session operations and the write loop exclusively owns `realtimeState` (`services/game-server/internal/networking/inbound_adapter.go:19-46`, `services/game-server/internal/networking/websocket_session.go:23-46`).

Resolution each tick:

1. Accept the requested target only if it has an active lifecycle entry and a current ship.
2. Otherwise fall back to the receiver’s active ship.
3. If the receiver has no active ship, fall back to the receiver’s retained server camera position.
4. Force self and the resolved target into ship membership even if outside the rectangle.

The lifecycle check is necessary because the client’s current spectate rules define eligibility as active plus visually available (`client/scripts/gameplay/spectate/spectate_menu_state.gd:44-57`). The server should echo the resolved target in receiver overlay state, e.g. `view_target_id`, so the client can distinguish accepted, rejected, and automatically cleared requests. Overlay is the existing receiver-specific record (`services/game-server/internal/protocol/realtime/records.go:50-63`).

Leaving-interest behavior

No new despawn packet is needed:

- Filtering an ID out of the current receiver projection causes `CompareLaneRecordFields` to produce a delete against that receiver’s previous committed projection (`services/game-server/internal/protocol/realtime/delta.go:76-134`).
- Ship, asteroid, and bullet deletes are moved into their reliable lifecycle candidates (`services/game-server/internal/protocol/realtime/lane_candidate_world.go:43-79`).
- Pickup deletes stay in the reliable world delta (`services/game-server/internal/protocol/realtime/lane_candidate_world.go:82-85`).
- The world/lifecycle transaction is committed only after successful transmission, preserving baseline membership under backpressure (`services/game-server/internal/networking/websocket_write.go:84-150,177-184`).
- The client already applies those deletes to caches and presentation nodes (`client/scripts/protocol/realtime/world_lane_applier.gd:67-100,202-212`, `client/scripts/world/world_sync.gd:91-135`).
- Re-entry naturally produces a normal lifecycle create. It must contain the complete reliable record before subsequent hot updates are useful.

4. Low-cadence offscreen-player locator design

Proposed: use the existing reliable, baseline-backed session lane rather than adding another negotiated WebRTC channel.

Why session is the correct path

- It already carries every player session and authoritative lifecycle status, independent of world visibility (`services/game-server/internal/protocol/realtime/projection_session.go:20-63`).
- The client already maintains session records as a full/delta cache (`client/scripts/protocol/realtime/session_lane_state.gd:4-26`).
- A new negotiated channel would require both peers to create and wait for it; the current client and server enumerate an exact shared channel set and readiness requires all channels (`services/game-server/internal/networking/webrtc_transport.go:27-41`, `client/scripts/networking/webrtc/webrtc_transport.gd:4-16,149-163`).
- Locator delivery is low-cadence player meaning, not render-frequency movement. Keeping it off `ship_delta` ensures distant ships do not receive 60 Hz movement.

Contract shape

Extend `SessionPlayerRecord`/`SessionPlayerWireRecord` with:

- `locator_present`
- `locator_x`
- `locator_y`
- `team_id`

At a 6-tick/10 Hz cadence:

- sample every active player’s authoritative ship position and team;
- set `locator_present = false` for sessions without an active ship;
- between sampling ticks, copy locator fields from the previous committed session projection so ordinary session candidate construction does not accidentally publish 60 Hz positions;
- sample immediately for a full baseline, player lifecycle transition, view-target change, or missing prior locator.

The existing session delta is field-sparse, so cadence samples produce only changed locator fields rather than resending full player records (`services/game-server/internal/protocol/realtime/delta.go:324-382`). Position fields should use the existing physical `position` quantization policy, as current session spawn and world coordinates do (`shared/packets/realtime_wire.toml:1183-1234`).

Client application

- Extend `SessionLaneState.player_sessions` decoding to retain locator fields.
- Add an active, non-legacy locator presentation helper under `client/scripts/world/`; do not add policy under `client/legacy`.
- Convert locator server positions into wrapped visual positions relative to `WorldSync`’s current view anchor using the existing server-to-visual seam (`client/scripts/world/world_sync.gd:244-255`).
- Change `GameplayPresentationFlow`’s indicator position provider from rendered remote nodes to locator-derived positions. The indicator controller itself already accepts a generic target-position dictionary (`client/scripts/gameplay/presentation/gameplay_presentation_flow.gd:12-24,32-44`, `client/scripts/gameplay/presentation/os_indicator_controller.gd:25-59`).
- Derive indicator hue from locator `team_id`, falling back to the existing deterministic/fallback player hue policy (`client/scripts/gameplay/presentation/player_hue_presenter.gd:93-113`).
- Change `SpectateMenuState` to enumerate active locator-present players rather than world ships, because distant ships will intentionally not exist in `WorldLaneState` (`client/scripts/gameplay/spectate/spectate_menu_state.gd:44-57`).
- On spectate selection, send `view_target_request`; retain the old anchor until the echoed resolved target and its reliable ship create are both present. Only then call `focus_camera_on_player`. The current immediate local focus assumes the target node already exists and therefore is unsafe after interest filtering (`client/scripts/gameplay/spectate/gameplay_spectate_flow.gd:33-54`, `client/legacy/player_render/player_sync.gd:52-57`).

5. Server lane, candidate, baseline, and budget changes

Candidate assembly

- Add a receiver projection context to `BuildActiveRealtimeResultForGame` and `assembleRealtimeLaneCandidates`, or store the resolved target as a prepared per-call input. Do not mutate `RealtimeSessionState` concurrently from inbound handling; it is write-loop-owned (`services/game-server/internal/networking/websocket_session.go:36-38`, `services/game-server/internal/protocol/realtime/active.go:35-43`).
- Filter only the world projection. Overlay remains receiver-specific, session remains global player meaning, and events remain unchanged in the first entity-interest slice (`services/game-server/internal/protocol/realtime/planner.go:13-38`).
- Build hysteresis against the committed `WorldWireFullPacket`, not the last computed but unsent projection (`services/game-server/internal/protocol/realtime/lane_candidate_world.go:21-35`, `services/game-server/internal/protocol/realtime/baseline.go:168-186`).

Baseline and lifecycle correctness

- A full world baseline must contain only the initial interested set plus forced self/target.
- A world delta must compare the previous filtered projection with the newly filtered projection.
- Hot projections must continue to be seeded from or membership-synchronized with the filtered world projection (`services/game-server/internal/protocol/realtime/hot_lane_projection.go:105-181`).
- Do not commit an interest transition before the reliable world/lifecycle transaction succeeds. Existing commit grouping provides this invariant and should receive an explicit regression test (`services/game-server/internal/networking/websocket_write.go:139-150,177-184`).

Budget and prioritization

Verified current limitations:

- The scheduler has a 500-byte target, but required candidates and all real hot chunks are included regardless of remaining budget (`services/game-server/internal/protocol/realtime/size_estimate.go:3-8`, `services/game-server/internal/protocol/realtime/scheduler.go:25-58`).
- Candidate records currently estimate one generic record rather than their actual record count (`services/game-server/internal/protocol/realtime/candidate_policy.go:45-64`).
- Hot chunking enforces a 1200-byte per-packet cap but does not cap aggregate same-tick output (`services/game-server/internal/protocol/realtime/hot_lane_chunker.go:106-123,142-164`, `services/game-server/internal/protocol/realtime/realtime_hardcap_chunker.go:38-98`).

Proposed changes:

1. Make candidate estimates record-aware, including actual create/update/delete counts and locator updates.
2. Keep reliable lifecycle/world membership candidates required.
3. Reserve hot priority in this order:
   - forced self ship update;
   - forced spectated-target ship update;
   - other interested ships by wrapped distance;
   - bullets by wrapped distance;
   - asteroids by wrapped distance;
   - locator sample/session delta;
   - lower-urgency pickup/session changes as their existing delivery semantics permit.
4. Preserve separate physical hot lanes, but sort each hot lane’s records by forced status and wrapped distance before chunking.
5. Schedule all chunks of one hot sequence atomically. The client applies chunked hot sequences only after complete assembly, so selecting an incomplete subset wastes bandwidth and cannot advance the projection safely (`client/scripts/protocol/realtime/world_lane_applier.gd:58-65,73-95`).
6. If an entire hot sequence does not fit the advisory aggregate budget, defer it and do not commit its hot projection. The next tick will supersede it from the last successfully sent projection.
7. Never budget-drop reliable interest deletes. A missing delete leaves stale entities indefinitely; lifecycle candidates are correctly classified as required and critical today (`services/game-server/internal/protocol/realtime/candidate_policy.go:3-21,24-42`).
8. Keep hard-cap chunking after record ordering/filtering. Interest filtering should reduce chunk counts, but it must not weaken the existing per-message cap (`services/game-server/internal/protocol/realtime/realtime_hardcap_chunker.go:38-98,134-180`).

7. Concrete tests and important failure modes

Server tests

1. Visibility primitive:
   - wrapped inclusion across all world edges;
   - exact enter/exit boundaries;
   - invalid/zero dimensions use clamped defaults;
   - simulation visibility remains behaviorally unchanged.
   Existing visibility tests provide the correct home and boundary style (`services/game-server/internal/game/visibility_test.go:11-39`).

2. Interest projection:
   - two receivers at different anchors get different world projections from one immutable frame;
   - no entity is removed from authoritative `Game.entities`;
   - all four entity classes use wrapped distance;
   - initial full baseline contains only enter-region entities.

3. Hysteresis:
   - new entity outside enter but inside exit remains absent;
   - previously committed entity between enter and exit remains;
   - entity outside exit produces one delete;
   - jitter around the visible edge does not alternate create/delete;
   - a blocked reliable write leaves the committed membership unchanged.

4. Self/spectate:
   - self remains present outside the selected target’s region;
   - valid active target remains present;
   - inactive, eliminated, missing, or malformed targets fall back;
   - target change produces target create and old-region deletes in one reliable transaction;
   - target death clears echoed target and falls back without mutating simulation camera views.

5. Baseline/lifecycle:
   - interest exit produces ship/asteroid/bullet lifecycle delete and pickup world delete;
   - re-entry produces complete lifecycle create;
   - hot projection membership is removed only after world commit;
   - resync full reflects current interest rather than global state.
   Existing baseline storage and lifecycle generation tests are the right neighboring suites (`services/game-server/internal/protocol/realtime/baseline_test.go:67-103,129-167`, `services/game-server/internal/protocol/realtime/lane_candidate_lifecycle.go:3-58`).

6. Locator cadence:
   - positions change only every six ticks;
   - non-sample ticks preserve the previous locator projection while other session fields can change;
   - full baseline and lifecycle/view-target transitions force a sample;
   - inactive players set `locator_present = false`;
   - locator changes produce sparse session updates.

7. Budget:
   - estimates reflect record counts;
   - lifecycle deletes remain included over budget;
   - forced self/target hot updates precede other hot records;
   - incomplete hot chunk groups are never selected;
   - deferred hot candidates do not advance their projection;
   - per-packet encoded size remains at or below 1200 bytes.
   Current scheduler and hard-cap tests provide direct extension points (`services/game-server/internal/protocol/realtime/scheduler.go:14-58`, `services/game-server/internal/protocol/realtime/hot_lane_chunker_test.go:123-162`).

8. Networking:
   - inbound target requests are stored per session;
   - one session cannot change another session’s view;
   - target state resets on room/player/match identity changes;
   - blocked world/lifecycle group does not block session locator progress;
   - failed writes do not commit interest membership.
   The current write path already has independent-group tests and receiver-specific state (`services/game-server/internal/networking/websocket_write.go:84-150`, `services/game-server/internal/protocol/realtime/baseline_test.go:204-218`).

Client tests

1. Generated compact descriptor tests for every new full/update field.
2. `SessionLaneState` full and sparse-delta locator merge tests.
3. Indicator tests proving:
   - distant locator without a world ship creates an indicator;
   - in-view hot ship does not get a duplicate indicator;
   - missing/inactive locator removes the indicator;

Important failure modes

- Using the spectated target to mutate `game.cameraViews` would change authoritative spawn/retention behavior; projection must use a copied view context instead (`services/game-server/internal/game/visibility.go:52-88`).
- Using computed rather than committed membership for hysteresis can lose a required delete under backpressure; membership must derive from the stored world projection (`services/game-server/internal/protocol/realtime/baseline.go:83-99,152-187`).
- Hot movement arriving before lifecycle create is already possible across channels. The existing lifecycle gate protects reliable baseline relationships, while hot updates buffer or ignore unknown entities; tests must preserve this behavior (`client/scripts/protocol/realtime/realtime_router.gd:92-112`, `client/scripts/protocol/realtime/world_lane_state.gd:166-180`).
- Immediate client camera focus can fail for a distant target because no ship node exists until the target enters the filtered world. Target activation must wait for the reliable create (`client/legacy/player_render/player_sync.gd:52-57`).
- Making locators 60 Hz would simply move the bandwidth problem to the reliable session lane. Cadence must be enforced while constructing the session projection, not only by scheduler priority.
- Adding a new physical negotiated channel without compatibility/version handling can prevent transport readiness because both peers require the exact channel set (`services/game-server/internal/networking/webrtc_transport.go:27-41`, `client/scripts/networking/webrtc/webrtc_transport.gd:149-163`).
- Offscreen indicators must not read stale world-node positions after the ship lifecycle delete; locator state must be their sole position source (`client/scripts/gameplay/presentation/gameplay_presentation_flow.gd:32-44`).
- Event batches are currently broadcast to every player and are outside this hot-entity slice (`services/game-server/internal/game/events.go:109-116`). If “interest” later includes presentation events, filtering must occur before event candidate/drain selection so skipped events cannot accumulate or be incorrectly drained (`services/game-server/internal/game/presentation_events.go:22-62`).
- Locators must not become a new gameplay-targeting authority. The server remains authoritative for target validation; locator positions are presentation-only.
- Session-lane locator growth can become material at large player counts. Sparse updates, quantization, encoded-byte metrics, and a measured maximum supported player count should gate rollout.
