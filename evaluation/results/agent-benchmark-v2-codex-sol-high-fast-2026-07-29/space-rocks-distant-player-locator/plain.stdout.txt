Investigated revision `460da4af`. The smallest correct change is a separate low-rate, coarse `player_locator` snapshot for indicators. Distant players must remain absent from receiver-filtered `ship_delta`; the locator must not create ship nodes or enter authoritative/render world state.

## Verified current behavior

- The server publishes one immutable frame containing every live ship and returns receiver wrappers over the same player map; only identity, lives, and pending events are currently receiver-specific (`services/game-server/internal/game/presentation_snapshot.go:22-30`, `services/game-server/internal/game/presentation_snapshot.go:66-113`).
- World projection enumerates every `snapshot.Players` entry, and ship hot projection extracts each ship’s `id/x/y/rotation/thrusting`. Changed values become `ship_delta` candidates (`services/game-server/internal/protocol/realtime/projection_world.go:16-38`, `services/game-server/internal/protocol/realtime/hot_lane_projection.go:15-26`, `services/game-server/internal/protocol/realtime/lane_candidate_world.go:93-106`).
- `ship_delta` uses `sr.ships`, an unordered channel with zero retransmissions; `ships.lifecycle` is separate and ordered (`services/game-server/internal/networking/webrtc_transport.go:27-40`).
- On the client, `ship_delta` updates the world-lane ship records, which world sync applies to player rendering (`client/scripts/protocol/realtime/world_lane_applier.gd:58-71`, `client/scripts/world/world_sync.gd:91-101`).
- The remote-position cache is populated from interpolated rendered player nodes (`client/legacy/player_render/player_sync_interpolation.gd:7-32`). Gameplay composition supplies that cache directly to the indicator flow (`client/scripts/gameplay/gameplay_composition.gd:260-268`, `client/scripts/gameplay/presentation/gameplay_presentation_flow.gd:32-44`).
- `OSIndicatorController` has no independent location source: it draws indicators for supplied positions and deletes indicators whose IDs disappear (`client/scripts/gameplay/presentation/os_indicator_controller.gd:25-59`). Therefore, once a future receiver filter removes a distant ship from receiver world/render state, the existing indicator loses that player as a direct consequence.
- Interest-driven render removal would also erase the player’s cached target position and hue under current cleanup behavior (`client/legacy/player_render/player_sync.gd:199-205`). Full reset already clears all hue state (`client/scripts/gameplay/presentation/player_hue_presenter.gd:23-31`).
- Current realtime session projections and sequences are keyed by lane, and successful candidates overwrite the projection for their lane (`services/game-server/internal/protocol/realtime/baseline.go:27-45`, `services/game-server/internal/protocol/realtime/baseline.go:152-170`). A second packet family sharing `LaneShips` therefore needs family-local sequence/projection state.
- Rooms are capped at eight players, so an unchunked coarse locator snapshot remains tightly bounded (`services/game-server/internal/playerids/playerids.go:5`, `services/game-server/internal/rooms/constants.go:9-13`).

## Proposed smallest design

1. Add a `PlayerLocatorState` record containing `id`, `x`, `y`, `velocity_x`, `velocity_y`, and `active`. Publish an all-player locator map alongside the immutable presentation frame. For a live, non-pending ship, copy its authoritative position and velocity and set `active=true`; otherwise retain a fallback position but mark it inactive. Runtime ships already own position, velocity, and pending-despawn state (`services/game-server/internal/game/runtime/state.go:12-33`, `services/game-server/internal/game/runtime/ship.go:42-61`).

2. Keep this map outside receiver interest filtering. Receiver-filtered `Players` continues to determine render nodes, lifecycle membership, and full-rate `ship_delta`; `PlayerLocators` remains the small presentation-only overview.

3. Add a `player_locator` packet family on the existing logical `ships` lane and physical `sr.ships` channel—no new DataChannel. Encode the locator list as a compact fixed tuple with position quantization. Send a complete replacement snapshot approximately every 12 server ticks, plus immediately when locator membership or `active` changes. Periodic full replacement makes packet loss self-healing despite the channel being unreliable.

4. Give `player_locator` an independent family sequence and committed projection. Do not advance or replace `LaneShips`’ `ship_delta` state. Classify it as medium-priority, hot-supersedable, and exclude it from the scheduler rule that unconditionally includes real hot-lane chunks. This preserves bandwidth pressure relief and avoids corrupting ship-delta comparisons.

5. Add client `PlayerLocatorState` and `PlayerLocatorApplier` seams. Accept only increasing locator sequences, atomically replace the complete locator dictionary, record local monotonic receipt time, and clear on router/match reset. Add explicit routing through:

   - `server_packet_router.gd`
   - `server_packet_dispatcher.gd`
   - `client_inbound_coordinator.gd`
   - `realtime_packet_pipeline.gd`
   - `realtime_router.gd`
   - `realtime_presentation_state.gd`
   - `presentation_adapter.gd`

   Explicit routing is necessary because current dispatch recognizes only declared families and the pipeline rejects packet types absent from its generated descriptor index (`client/scripts/networking/inbound/server_packet_dispatcher.gd:33-85`, `client/scripts/networking/realtime/realtime_packet_pipeline.gd:72-86`, `client/scripts/protocol/realtime/realtime_router.gd:42-77`).

6. Add `WorldSync.get_remote_player_indicator_positions()` without changing `get_remote_player_visual_positions()`:

   - Start with actual rendered remote positions so nearby ships retain smooth hot interpolation.
   - Fill only missing IDs from fresh, active locators.
   - Exclude self and inactive players.
   - Extrapolate by velocity using receipt age, capped around `0.75s`.
   - Discard locator-only positions after roughly `2s` without refresh.
   - Convert authoritative coordinates through the existing wrap-aware view-anchor mapping (`client/scripts/world/player_render/player_render_api.gd:140-145`, `client/legacy/player_render/local_visual_sync.gd:35-50`).

   Keeping the existing position method unchanged prevents coarse locators from leaking into targeting, which currently consumes rendered remote positions (`client/scripts/gameplay/targeting/target_position_source.gd:21-40`).

7. Change only the presentation composition provider from `get_remote_player_visual_positions` to `get_remote_player_indicator_positions`. `OSIndicatorController` and its scene need no changes.

8. Preserve cached remote hues when a render node disappears because of interest filtering; let match reset clear the bounded cache. Locator membership controls whether an indicator exists, so departed players do not remain visible.
